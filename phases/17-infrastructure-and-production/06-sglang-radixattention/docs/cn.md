# SGLang 和 RadixAttention 用于前缀密集型工作负载

> SGLang 将 KV cache（键值缓存）作为一级、可重用资源，存储在 radix tree（基数树）中。与 vLLM 按 FCFS（先到先服务）调度请求不同，SGLang 的 cache-aware（缓存感知）调度器优先处理具有更长共享前缀的请求——实际是一种深度优先的基数遍历算法，使得“热点”分支常驻在 HBM（高带宽内存）中。在 Llama 3.1 8B 模型上，针对 ShareGPT 风格的 1K 提示，SGLang 达到了约 16,200 tok/s，而 vLLM 约为 12,500，领先约 29%。在前缀密集型 RAG 工作负载中，优势甚至达到 6.4 倍。在语音克隆类工作负载中，缓存命中率超过 86%。2026 年已部署于 xAI、LinkedIn、Cursor、Oracle、GCP、Azure、AWS 等超过 40 万个 GPU 上。需要注意的是，当前缀排序不一致时，6.4 倍的优势会消失——排序是工程师的调节杆。

## 学习目标

- 绘制 RadixAttention（基数注意力）的示意图：前缀如何存储在基数树中，KV 块如何在以相同分支为根的序列间共享。  
- 解释缓存感知调度的原理，以及为什么对前缀密集型流量采用 FCFS 是错误的。  
- 根据前缀缓存命中率和提示长度分布，计算工作负载的预期加速比。  
- 说出使 6.4 倍优势变为现实而非流失的提示顺序规范。

## 问题

经典服务端把每个请求的提示看作不透明的字符串。即使 5,000 个 RAG 请求都以相同的 2,000 字符系统提示加相同的检索前置内容开头，vLLM 也会预填充那个 2,000 字符的前缀 5,000 次。GPU 不断重复同样的工作。

观察到：在 agentic 和 RAG 工作负载中，提示几乎总是共享长前缀。系统提示、工具模式、少量示例、检索头、对话历史——这些内容跨请求重复出现。如果你把该前缀对应的 KV cache 缓存起来并重用，就不需要每次重复预填。

RadixAttention 正是这么做的。Token（子词）被索引在基数树中；每个节点拥有自身路径对应的 token 序列的 KV 块。新请求在树上遍历：路径上 token 相符的节点复用该节点的 KV 块。预填成本仅与新后缀长度成正比，而非整个提示长度。

难点在于调度。如果两个请求共享 2,000 token 前缀，而第三个只共享同一个前缀的 200 token，你希望同时处理那两个长前缀请求，使得长前缀常驻 HBM。FCFS 则相反——它服务先到的请求，可能让热点分支在下一个长前缀请求到来前被淘汰。

## 概念

### 作为 KV 索引的基数树

基数树（紧凑前缀树）用于存储 token 序列。每个节点拥有一段 token 范围及该范围计算得出的 KV 块。子节点将序列延长一个或多个 token。

```text
root
 |- "You are a helpful assistant..."  (2000 tokens, 124 KV blocks)
      |- "Context: <doc A>..."        (500 tokens, 31 blocks)
           |- "Question: Alice..."    (80 tokens, 5 blocks)
           |- "Question: Bob..."      (95 tokens, 6 blocks)
      |- "Context: <doc B>..."        (520 tokens, 33 blocks)
```

新请求携带系统提示 + "Context: <doc A>" + "Question: Carol"。调度器遍历树：系统前缀匹配（复用124块），doc-A 分支匹配（复用31块），只为 "Question: Carol" 分配新块（4块）。预填成本：4个新 token 的 KV 块。没用树之前：160 块。预填节省约 40 倍。

### 缓存感知调度

如果缓存频繁置换，则基数树复用无意义。两个关键策略：

1. **深度优先调度**。从队列选择下一个请求时，优先选择与当前活动集根节点相同分支的请求，保持热点分支常驻。  
2. **分支级 LRU（最近最少使用淘汰），非块级。** 淘汰整棵分支（从最短命叶子节点开始），而非单个块，使缓存结构与基数树结构匹配。

FCFS 违反了以上两点。例如，2,000 token 共享请求后面排着一个只共享 50 token 的请求，2,000-token 分支可能会被提前淘汰去容纳 50-token 分支。

### 你需要记住的基准数据

- Llama 3.1 8B，H100，ShareGPT 1K 提示：SGLang ~16,200 tok/s，vLLM ~12,500 tok/s（约 29% 的优势）。  
- 前缀密集型 RAG（相同系统提示 + 相同文档，不同问题）：SGLang 优势最高达 6.4 倍。  
- 语音克隆工作负载：缓存命中率 86.4%。  
- SGLang 生产环境水平均缓存命中率 50-99%，取决于提示顺序规范。  
- 2026 年部署于超过 40 万个 GPU。

### 排序的坑

6.4 倍优势建立在一致的提示模板顺序上。例如，若客户端某些请求构造提示为 `[system, tools, context, history, question]`，而另一些为 `[system, context, tools, history, question]`，基数树无法识别共享前缀。在基数树看来，人类看起来共享的前缀实际上是两个不同的序列。

工程师的调节杆：提示模板就是缓存键。固定顺序。将一切不可变的部分（系统、工具、模式）放置最前，将检索上下文放后面，用户问题放最后。不要在前缀中夹杂动态内容。

研究真实案例：仅一次变更，把动态内容移出可缓存前缀，缓存命中率从 7% 跃升至 74%。

### RadixAttention 的优势与劣势

优势：  
- RAG（相同检索前置，不同问题）  
- Agent（相同工具模式，不同查询）  
- 长系统提示的聊天  
- 含重复前置的语音/视觉工作负载  

劣势（吞吐率回落到 vLLM 级别）：  
- 唯一提示的单轮生成（代码补全、无系统提示的开放式聊天）  
- 每个请求在前缀中交织唯一动态内容的动态提示  

### 为什么这是调度器问题，而非仅是内核问题

你可以将 KV 重用实现为内核技巧。SGLang 的洞察在于，重用只有调度器保持热点分支常驻时才有效。天真的“只要可重用就重用”策略，在混合负载下会导致缓存频繁置换。基数树索引的调度器使内核技巧实现了 29% 的生产优势。

### 与 vLLM 的关系

两者不是严格竞争关系。2026 年，vLLM 加入了前缀缓存（`--enable-prefix-caching`）和缓存感知路由器（Rust 实现的 vLLM Router）。差距缩小但未完全消失——SGLang 实现了纯基数树优先的全栈设计，vLLM 是后期拼接进去的。对以重用前缀为主的工作负载，SGLang 是默认选择；对无明显前缀模式的通用服务，vLLM 依然等效或更优。

## 使用教程

`code/main.py` 实现了一个玩具基数树 KV 缓存，并带有两个调度策略：FCFS 和缓存感知。对同一工作负载运行两种策略，报告前缀缓存命中率及吞吐变化。然后运行“乱序提示”工作负载，演示 6.4 倍优势消失。

## 部署

本课产出 `outputs/skill-radix-scheduler-advisor.md`。给定工作负载描述（提示模板形态、检索模式、并发租户数），生成提示排序建议和是否采用 SGLang 的决策指导。

## 关键词

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| RadixAttention | “SGLang 的东西” | 将 KV 缓存索引为基数树，实现共享前缀复用 KV 块 |
| 基数树（Radix tree） | “紧凑前缀树” | 树状结构，节点拥有 token 范围及其 KV 块 |
| 缓存感知调度器 | “热点分支优先” | 优先调度共享当前常驻分支的请求 |
| 前缀缓存命中率 | “有多少提示是免费的” | 从复用 KV 块服务的提示 tokens 的比例 |
| FCFS | “先到先服务” | 默认调度方式，会破坏前缀局部性 |
| 分支级 LRU | “淘汰叶子” | 按基数树结构匹配的淘汰策略 |
| 提示模板排序 | “缓存键” | 提示组成部分的顺序决定树能共享哪些子序列 |
| 系统提示固定 | “常驻前缀” | 保持不可变的系统部分常驻，避免频繁淘汰 |
