# 无服务器大型语言模型（LLM）的冷启动缓解

> 一个 20 GB 的模型镜像从冷启动到服务运行需要 5-10 分钟（7B）到 20 多分钟（70B）。在真正的无服务器环境中，这不是热启动——而是中断。缓解措施涵盖五个层面：预置节点镜像（AWS 上的 Bottlerocket，双卷架构）、模型流式加载（NVIDIA Run:ai Model Streamer，vLLM 原生支持）、GPU 内存快照（Modal 检查点，重启速度提升最多 10 倍）、预热池（`min_workers=1`）、分层加载（ServerlessLLM 的 NVMe→DRAM→HBM 管线，延迟降低 10-200 倍），以及传递输入令牌（KB）而非 KV 缓存（GB）的实时迁移。Modal 将冷启动时间发布为 2-4 秒底线；Baseten 默认 5-10 秒，预热后低于一秒。本课教你如何测量、预算并叠加这五个层级的缓解措施。

**类型：** 学习  
**语言：** Python（标准库，玩具冷启动路径模拟器）  
**先决条件：** 第17阶段 · 02（推断平台经济学）、第17阶段 · 03（GPU 自动扩缩）  
**时长：** 约 60 分钟

## 学习目标

- 列举冷启动缓解的五个层级，并为每个层级命名一个工具或模式。
- 计算一个 70B 模型的总冷启动时间，即（节点准备）+（权重下载）+（权重加载进 HBM）+（引擎初始化）之和。
- 解释为何实时迁移转移输入令牌（KB）而非 KV 缓存（GB），以及其代价是什么（重新计算）。
- 说明预热池的权衡（支付空闲 GPU 费用或接受冷启动尾延迟）及 `min_workers > 0` 成为强制条件的 SLA 阈值。

## 问题描述

你的无服务器 LLM 端点夜间缩容为零。早上 8 点流量激增。第一个请求等待期间：

1. Karpenter 准备一个 GPU 节点：45-60秒。  
2. 容器拉取 30 GB 的含权重镜像：120-300秒。  
3. 引擎将权重加载进 HBM：根据模型大小及存储速度，45-120秒不等。  
4. vLLM 或 TRT-LLM 初始化 CUDA 图、KV 缓存池、分词器：10-30秒。

总计：220-510 秒（约 3-8 分钟）才返回第一个令牌。你的 SLA 是 2 秒。你启用了预热池（`min_workers=1`），问题似乎消失——但你现在要为一块空闲 GPU 持续支付费用。如果你的服务有 5 个产品，每个产品一个预热副本，那就是 5 × 24 × 30 = 3,600 GPU 时/月，无论是否有用户请求。

冷启动缓解就是如何在保持无服务器经济性的同时近似实现全天候在线的延迟表现。

## 概念详解

### 层级 1 — 预置节点镜像（Bottlerocket）

在 AWS 上，Bottlerocket 的双卷架构将操作系统和数据分离。对数据卷的快照中预拉取容器镜像；在 `EC2NodeClass` 中引用该快照 ID。新节点启动时，权重已经在本地 NVMe 上——步骤 2 和部分步骤 3 消失。与 Karpenter 原生兼容。典型节省：每次冷启动省 2-4 分钟（大型模型）。

GCP 等效方案：自定义虚拟机镜像中预置容器层。Azure 的做法则是托管磁盘快照，流程类似。

### 层级 2 — 模型流式加载（Run:ai Model Streamer）

不是等待整个文件加载完成再响应第一个请求，而是权重分层流入 GPU 内存，加载到第一个 Transformer 块即可开始处理。NVIDIA 的 Run:ai Model Streamer 在 vLLM 2026 版本内原生支持。兼容 S3、GCS 和本地 NVMe。通过重叠 I/O 和计算准备，权重加载时间几乎减少一半。

### 层级 3 — GPU 内存快照（Modal）

Modal 在首次加载后对 GPU 状态（权重、CUDA 图、KV 缓存区域）做检查点。后续重启直接在 HBM 中反序列化，然后继续——比重新初始化快 10 倍。这是最接近“2 秒启动热 GPU”的方案。权衡点是快照针对特定 GPU 架构，如果 Karpenter 将你迁移到不同型号节点，需重新检查点。

### 层级 4 — 预热池（min_workers=1）

最简单的缓解方法：保持至少一份副本随时就绪。代价是全天候支付一个 GPU 时价。对小模型来说成本惨烈（付 0.85-1.50 美元/时以避免 30 秒冷启动），大模型则较为合理（付约 4 美元/时以避免 5 分钟冷启动）。使 `min_workers > 0` 成为强制条件的 SLA 阈值一般是 70B+ 模型 P99 TTFT 小于 60 秒。

### 层级 5 — 分层加载（ServerlessLLM）

ServerlessLLM 将存储看作阶层结构：NVMe（快且大）、DRAM（中等且分层）、HBM（小且瞬时）。权重预载入 DRAM，按需加载到 HBM。论文报告对比朴素的磁盘直达 HBM 方案，冷启动延迟降低 10-200 倍。生产应用尚早，但已有与 vLLM 的集成。

### 层级 6 — 实时迁移（附加模式）

节点不可用时（如抢占或节点驱逐），传统做法是冷启动新副本并排空请求队列。实时迁移新做法是把输入令牌（千字节级）传到装载了模型的目标节点，并在目标节点重新计算 KV 缓存。重新计算比在网络上传输数 GB KV 缓存更经济。适用于解耦部署。

### 预热池数学分析

对于 P99 TTFT SLA 为 2 秒的服务，问题不是“是否使用预热池”，而是“预热副本数量是多少、哪些路径使用”。

- 高价值交互路径（实时聊天、语音代理）：`min_workers=1-2`。  
- 后台批处理路径（夜间分类）：接受 scale-to-zero，冷启动等待 5-10 分钟容忍。  
- 高级套餐：按租户设定 `min_workers` 并分配专用容量。

### 优化前先测量

70B 新节点冷启动过程（示例）：

| 阶段           | 时间  | 缓解措施                             |
|----------------|-------|------------------------------------|
| 节点准备       | 50秒  | Bottlerocket + 预置镜像，预热池      |
| 镜像拉取       | 180秒 | 预置数据卷（消除该步骤）             |
| 权重加载进 HBM | 75秒  | 模型流式加载（减半）；GPU 快照（消除）|
| 引擎初始化     | 20秒  | 持久 CUDA 图缓存                     |
| 首次前向推理   | 3秒   | 最小固有延迟                        |
| **总冷启动**    | **328秒** |                                    |
| **缓解后总计**  | **约 15秒** | 约 22 倍延迟减少                      |

## 关键词汇

| 词汇            | 常见说法           | 实际含义                            |
|-----------------|--------------------|-----------------------------------|
| 冷启动          | “大停顿”           | 新副本从请求到首令牌的时间         |
| 预热池          | “始终在线最低容量” | `min_workers >= 1` 保持至少一副本待命 |
| 预置镜像        | “烘焙 AMI”         | 预装容器权重的节点镜像             |
| Bottlerocket    | “AWS 节点操作系统” | 支持双卷快照的 AWS 容器优化操作系统 |
| 模型流式加载    | “流式加载”         | 权重加载与计算准备重叠             |
| GPU 快照        | “HBM 检查点”       | 加载后 GPU 状态序列化，重启反序列化  |
| 分层加载        | “NVMe + DRAM + HBM”| 存储阶层结构，按需加载             |
| 实时迁移        | “移动输入令牌”      | 传输输入数据，目标节点重新计算 KV  |
| `min_workers`   | “预热副本数”       | 无服务器最低保活副本数             |
| scale-to-zero   | “全无服务器”        | 空闲时无成本，接受完全冷启动延迟    |
