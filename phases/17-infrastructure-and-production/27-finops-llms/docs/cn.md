# 大型语言模型（LLM）FinOps——单元经济学与多租户归因

> 传统的FinOps在LLM支出上失效。成本是基于token交易，而非资源运行时长。标签无法映射——API调用是一次交易，不是资产。工程决策（提示设计、上下文窗口、输出长度）即财务决策。2026年操作手册有三大归因维度，需在第一天即埋点：用户级（`user_id`）用于席位定价与扩容；任务级（`task_id` + `route`）用于产品界面成本与优先级；租户级（`tenant_id`）用于单元经济学与续约。四个token层——提示（prompt）、工具（tool）、记忆（memory）、响应（response）——合并计费掩盖真实支出。多租户产品的执行阶梯：租户速率限制（预期峰值的2-3倍，返回429+retry-after）；每日支出上限（合同上限的1.5-3倍，触发速率限制收紧+告警）；花费z分数大于4的杀死开关（自动暂停+呼叫值班）。归因模式：标签聚合、遥测关联（trace-ID → 计费；最高精度）、采样推断、模型分配、事件溯源、实时流处理。单元指标：每解决查询成本，每生成产物成本——而非$/百万token。事后标签永远无法覆盖，需在请求创建时埋点。

**类型:** 学习  
**语言:** Python（标准库，带杀死开关的简单成本归因模拟器）  
**先修:** 阶段17 · 13（可观测性）、阶段17 · 14（缓存）  
**时长:** 约60分钟

## 学习目标

- 解释为何传统FinOps（标签+分层）在LLM支出上失效，并列举三大归因维度。
- 枚举四个token层（提示、工具、记忆、响应）及单桶计费为何掩盖成本。
- 设计一个多租户产品的执行阶梯（速率限制 → 支出上限 → 杀死开关）。
- 选择一种单元指标（每解决查询/产物成本）替代$/百万token。

## 问题描述

账单报40,000美元，但你不知道：  
- 哪个租户花了这笔钱。  
- 是哪个产品功能驱动了支出。  
- 任何单个用户是否滥用。  
- 是提示膨胀、工具调用还是记忆放大导致的。

云资源（EC2、S3）支持提供商端标签并映射到明细行，标签聚合可行。而LLM API调用不自动标签——必须在调用端打上用户/任务/租户标签并传递。事后归因总会漏掉边缘案例。

## 概念解析

### 三大归因维度

**用户级**（`user_id`）：谁花了多少钱。促成席位定价、扩容讨论，识别高价值用户。

**任务级**（`task_id` + `route`）：哪个产品界面产生了成本。指导功能优先级与剔除昂贵功能。

**租户级**（`tenant_id`）：哪个客户盈利。驱动单元经济与续约定价、分层门槛。

第一天即在调用端埋点这三维度，事后归因永远不及。

### 四个token层

| 层级   | 例子                   | 典型占比    |
|--------|------------------------|-------------|
| Prompt | 系统＋用户输入          | 40-60%      |
| Tool   | 工具调用结果回填        | 20-40%（Agent工作负载） |
| Memory | 之前对话/检索文档       | 10-30%      |
| Response | 模型输出              | 10-30%      |

将四层合并计费会使优化盲区，务必在归因方案中拆分。

### 执行阶梯

1. **租户速率限制**。取预期峰值的2-3倍。返回429状态代码和`Retry-After`头。租户体验阻滞，无意外账单。

2. **每日支出上限**。1.5-3倍合同上限。触发后收紧速率限制且告警客户成功团队。

3. **杀死开关**。当租户支出z分数超过4时自动生效。自动暂停租户，呼叫值班，升级到运维和客户成功。

### 归因模式

- **标签聚合**：打元数据标签，事后聚合。简单但粗糙。
- **遥测关联**：基于trace ID将追踪关联到计费。最高精度。成熟团队的做法。
- **采样推断**：采样5-10%，再按比例放大。成本效益高，粗略开销估计，但易丢失尾部。
- **基于模型分配**：用回归推断成本驱动因子。适合无标签的历史数据。
- **事件溯源**：将成本事件写入流（Kafka / Kinesis）。实时处理。
- **实时流处理**：子秒级仪表盘更新。

### 单元指标即成本指标

$/百万token 是厂商话术。产品指标应为：

- 每解决的支持工单成本。
- 每生成的文章成本。
- 每成功Agent任务成本。
- 每用户会话分钟成本。

将成本绑定到产品结果，否则优化毫无锚点。

### 成本归因追踪结构

```text
trace_id: abc123
  user_id: u_42
  tenant_id: t_7
  task_id: task_classify_doc
  route: model_haiku
  layers:
    prompt_tokens: 1800
    tool_tokens: 600
    memory_tokens: 400
    response_tokens: 150
  cost_usd: 0.0135
  cached_input: true
  batch: false
```

每次调用时发出，存入数据湖，按维度聚合。阶段17 · 13可观测性栈承载此数据。

### 复合节省栈

栈结构：缓存 + 批处理 + 路由 + 网关。四者合并效果如下：  
- L2缓存（阶段17 · 14）：输入成本约降10倍。  
- 批处理（阶段17 · 15）：节省50%。  
- 路由到廉价模型（阶段17 · 16）：节省60%。  
- 网关效率（阶段17 · 19）：冗余和重试。  

最优叠加可达天真的5-10%成本。大多数团队激活2-3个手段，少数全开四杠杆。

### 你应该记住的数据点

- 归因维度：用户级、任务级、租户级。
- 四个token层：提示、工具、记忆、响应。
- 杀死开关：支出z分数 > 4。
- 单元指标：每解决查询成本，不是$/百万token。
- 叠加优化：可实现约5-10%基线成本。

## 关键词

| 术语             | 常用说法          | 实际含义               |
|------------------|-------------------|------------------------|
| 用户级归因       | “用户层成本”     | 每次调用都打 `user_id` 标签  |
| 任务级归因       | “功能成本”       | 用 `task_id` + `route` 标识产品界面 |
| 租户级归因       | “客户成本”       | `tenant_id`，驱动单元经济学  |
| 四个token层      | “成本层次”       | 提示+工具+记忆+响应      |
| 速率限制         | “429保护”        | 网关层面按租户限额执行    |
| 每日支出上限     | “日限额”         | 租户预算限制并告警      |
| 杀死开关         | “自动暂停”       | 支出z分 > 4触发自动挂起  |
| 每解决成本       | “产品单元指标”   | 成本关联产品结果，而非token |
| 遥测关联         | “trace-to-billing”| 最精确的归因方式        |
