# LLM 生产环境混沌工程

> 到 2026 年，LLM 混沌工程成为独立学科。生产环境做实验的前提条件：定义好的 SLI/SLO，trace+metric+log 可观测性，自动回滚，运行手册，值班。架构有四个层面：控制层（实验调度器）、目标层（服务、基础设施、数据存储）、安全层（守护、终止、流量过滤）、可观测层（指标、追踪、日志）；反馈环路用于调整 SLO。守护措施是必需的：燃烧率告警当日错误预算消耗超过预期 2 倍时暂停实验；抑制窗口 + trace-ID 关联去重告警噪声。节奏安排：每周小规模金丝雀 + SLO 复盘；每月演练日 + 事故复盘；每季度跨团队韧性审核 + 依赖映射。LLM 专属实验：内存超载、网络故障、服务提供商中断、格式错误的提示词、KV 缓存驱逐风暴。工具链：Harness Chaos Engineering（LLM 派生推荐，爆炸半径缩减，MCP 工具集成）；LitmusChaos（CNCF）；Chaos Mesh（CNCF Kubernetes 原生）。

**类型：** 学习  
**语言：** Python（标准库，简单混沌实验运行器）  
**先决条件：** 第 17 阶段 · 23（AI 的 SRE），第 17 阶段 · 13（可观测性）  
**时间：** 大约 60 分钟

## 学习目标

- 列出五个混沌工程先决条件（SLI/SLO、可观测性、回滚、运行手册、值班）并说明缺失任何一项为何会破坏实践。  
- 绘制四个层面（控制、目标、安全、可观测）和反馈环路调整 SLO 的示意图。

- 根据技术栈选择工具：Harness、LitmusChaos 或 Chaos Mesh。

## 问题描述

传统技术栈的混沌测试已经成熟。LLM 技术栈增加了新的故障模式。一个带有毒字符的 4K Token 提示会造成分词器卡顿 12 秒。上游服务返回 429；你的网关重试；服务因重试放大的并发而 OOM。KV 缓存驱逐风暴在突发负载下导致重新预填充级联，饱和计算资源。

这些问题都无法通过单元测试发现。混沌工程让你在用户发现之前就洞悉这些问题。

## 概念详解

### 先决条件

切勿在生产环境中运行混沌测试，除非具备：

1. **SLI/SLO** — 已定义的服务级指标和目标。  
2. **可观测性** — 包括追踪、指标、日志，并接入仪表盘。  
3. **自动回滚** — 第 17 阶段 · 20 策略标记回滚。  
4. **运行手册** — 结构化文档，第 17 阶段 · 23。  
5. **值班** — 有人及时响应。

缺一不可，否则混沌会变成真实事故。

### 四个层面 + 反馈环路

**控制层** — 实验调度器（Litmus workflow，Chaos Mesh 调度，Harness UI）。  

**目标层** — 服务、Pod、节点、负载均衡器、数据存储。  

**安全层** — 终止开关、抑制窗口、爆炸半径限制、错误预算门控。  

**可观测层** — 常规指标 + trace-ID 相关性用于区分混沌导致与自然失败。  

**反馈环路** — 结果反馈到 SLO 调整、运行手册更新、代码修复。

### 守护措施是必须的

- **燃烧率告警**：当每日错误预算燃烧率超过预期的 2 倍时暂停实验。  
- **抑制窗口**：实验爆炸半径内非实验警报静默。  
- **trace-ID 关联**：所有实验诱发的错误均携带标签，方便值班人员去重。

### 五个 LLM 特定实验

1. **内存超载** — 通过发送长上下文请求并发实现 KV 缓存抢占风暴。观察：服务是否优雅释放资源或崩溃？  

2. **网络故障** — 断开推理网关与提供者之间的连接。观察：故障恢复是否在 SLA 内启动？（第 17 阶段 · 19）  

3. **服务提供商中断模拟** — OpenAI 100% 返回 429。观察：路由是否切换到 Anthropic？（第 17 阶段 · 16, 19）  

4. **格式错误提示词** — 注入导致分词器卡顿的负载（如深度嵌套的 Unicode、巨大的 UTF-8 码点）。观察：单个请求是否阻塞工作线程？  

5. **KV 缓存驱逐风暴** — 通过饱和 vLLM 块预算强制驱逐。观察：LMCache 是否恢复或服务是否降级？

### 节奏安排

- **每周** — 在预发布环境做小规模金丝雀测试，生产环境可能覆盖 5%。  
- **每月** — 具体场景下的定期演练日；跨团队共同参与；事故复盘。  
- **每季度** — 跨团队韧性审核；更新依赖关系图。

### 工具

- **Harness Chaos Engineering** — 商用；AI 派生实验推荐；爆炸半径缩减；MCP 工具集成。  
- **LitmusChaos** — CNCF 毕业项目；基于 Kubernetes workflow。  
- **Chaos Mesh** — CNCF 沙箱；Kubernetes 原生 CRD 风格。  
- **Gremlin** — 商用；广泛支持。  
- **AWS FIS** / **Azure Chaos Studio** — 托管云服务。

### 从小开始

首个实验：在稳定流量下杀死一个解码副本 Pod。观察路由和恢复情况。如果运行正常且安全，逐步过渡到网络混沌实验。

首个 LLM 特定实验：注入一次 5 分钟的提供商 429。观察回退策略。大多数团队发现自己的回退路径未经充分测试。

### 必记数字

- 四个层面：控制、目标、安全、可观测。  
- 燃烧率暂停阈值：每日误差预算消耗超过预期的 2 倍。  
- 节奏：每周金丝雀，每月演练日，每季度审核。  
- 五个 LLM 实验：内存、网络、提供商、格式错误提示词、KV 驱逐风暴。

## 关键术语

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| SLI / SLO | “服务目标” | 指标 + 目标；必需先决条件 |
| Blast radius（爆炸半径） | “范围” | 受实验影响的服务/用户集合 |
| Burn-rate alert（燃烧率告警） | “预算门控” | 错误预算燃烧率 > 2 倍时触发 |
| Game day（演练日） | “每月演练” | 定期跨团队混沌演习 |
| LitmusChaos | “CNCF workflow” | CNCF 毕业项目，基于 Kubernetes workflow 的混沌工具 |
| Chaos Mesh | “CNCF CRD” | CNCF 沙箱项目，Kubernetes 原生的混沌工具 |
| Harness CE | “商业 AI 辅助” | Harness AI 推荐的混沌工程工具 |
| Malformed prompt（格式错误提示词） | “分词器炸弹” | 卡顿分词器的输入 |
| KV eviction storm（KV 驱逐风暴） | “抢占级联” | 大规模驱逐触发的重新预填充 |
