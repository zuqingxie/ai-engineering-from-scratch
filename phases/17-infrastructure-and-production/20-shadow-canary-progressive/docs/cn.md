# Shadow Traffic（影子流量）、Canary Rollout（金丝雀发布）和 Progressive Deployment（渐进部署）用于 LLMs（大语言模型）

> LLM 发布结合了软件部署中最难的部分：无单元测试、分散的失败模式、信号延迟。流程是（1）shadow mode（影子模式）——复制生产请求到候选模型，记录日志，比较且对用户零影响；能捕捉明显的分布问题，但不是质量保证；（2）canary rollout（金丝雀发布）——流量逐步切换 10% → 25% → 50% → 75% → 100%，每步设闸门；追踪延迟分位数、每请求成本、错误/拒绝率、输出长度分布、用户反馈率；（3）稳定后进行不同方案的 A/B 测试。非确定性是不可约的——相同输入下不同运行间可能有高达 15% 的准确率波动，原因是 GPU 浮点数非结合性和批大小差异。成本是变量非常量——一个效果好 20% 的模型调用成本可能高出 3 倍。回滚速度决定成败：如果回滚需要重新部署，那你太慢了。策略存在 config/flags 中；模型存于带有固定摘要的注册表；回滚 = 立刻切换策略 + 恢复阈值 + 固定旧模型。

**类型：** 学习  
**语言：** Python（标准库，简易金丝雀渐进模拟器）  
**先修课程：** Phase 17 · 13（可观测性），Phase 17 · 21（A/B 测试）  
**时长：** 约 60 分钟

## 学习目标

- 区分 shadow mode（零影响对比）、canary（金丝雀实时渐进流量）、A/B（稳定后对比）。
- 列举 LLM 特有的五个金丝雀度量指标（延迟、每请求成本、错误/拒绝率、输出长度分布、用户反馈）。
- 解释为何 LLM 非确定性（最高 15%）改变了发布中“稳定”的定义。
- 设计秒级完成的回滚路径（策略切换）而非数小时（重新部署）。

## 问题描述

你发布了一个新模型。离线评测显示准确率提升 3%。上线生产。24 小时内成本上涨 40%，用户投诉率上涨 8%，有三张客户工单反馈“回答怪异”。你回滚。重新部署花费 3 小时。你的周末毁了。

这一切本可避免。影子模式能在任何用户感知前捕捉到 40% 的成本飙升。金丝雀模式应在用户投诉上升时停止在 10%。策略标志回滚只需 30 秒。纪律性弥合了“离线评测表现好”与“用户满意”之间的差距。

## 概念详解

### Shadow mode（影子模式）

候选模型接收与生产相同的请求；输出记录日志，而不返回给用户。对用户零影响。日志内容：

- 输出内容（与生产模型的差异）。
- Token 数量（成本差异）。
- 延迟。
- 拒绝和错误。

捕捉：成本暴涨、长度回退、明显拒绝变更、严重错误。不捕捉：用户感知的质量差异。影子模式是冒烟测试，不是质量测试。

### Canary rollout（金丝雀发布）

渐进流量切换，设有各种闸门。常规梯度：1% → 10% → 25% → 50% → 75% → 100%。每步闸门监控 5 个指标：

1. **延迟分位数** — P50、P95、P99。违例条件：金丝雀 P99 超过基线的 1.5 倍。
2. **每请求成本** — 混合成本。违例条件：超过基线 20%。
3. **错误/拒绝率** — 5xx 错误及明确拒绝。违例条件：是基线的 2 倍。
4. **输出长度分布** — 均值 + P99。违例条件：分布显著偏移。
5. **用户反馈率** — 负面反馈/工单数量。违例条件：超过基线的 1.5 倍。

### 非确定性是新的方差

相同输入产生不同输出。原因包括：

- GPU 浮点数非结合性（浮点运算顺序随批次变化）。
- 批大小差异（在 128 批 vs 16 批中的同一提示）。
- 采样（温度 > 0）。

实测显示同一评测集上跑多次，准确率波动可达 15%。发布中的“稳定”意味着指标处于预期方差范围内，而非与基线完全一致。设定闸门阈值时要高于噪声底线。

### 成本是变量

一个效果提升 20% 的模型，每次调用成本可能高出 3 倍。每请求成本是五个闸门之一。发布一个“更好”但破坏单元经济的模型属于回滚情况。

### 回滚是关键利器

- 策略标志（feature flag 系统）：配置中翻转百分比；耗时秒级。
- 模型固定（注册表摘要）：固定模型不会自动升级。
- 回滚 = 恢复标志 + 设置先前的固定摘要。秒级完成，不是小时。

如果你的系统回滚需要重新部署，请先修复再发布。

### 工具

**Argo Rollouts** / **Flagger** — Kubernetes 渐进交付控制器。整合 Istio/Linkerd 权重路由。

**Istio weighted routing** — 服务网格层级流量拆分。

**KServe / Seldon Core** — 具备金丝雀功能的模型服务。

**Feature flags（功能标志）** — LaunchDarkly、Flagsmith、Unleash。策略级切换，无需重新部署。

### 指标频率

金丝雀闸门依据流量量每 5-15 分钟检查一次。1% 流量、每分钟 10 请求，窗口数据点约 50-150 个——对延迟够用，但用户反馈噪音较大。10% 流量约 10 倍数据。每步递进应暂停足够时间收集样本。

### A/B 测试步骤可选

如果新模型行为迥异（不同表现、成本曲线、风格），且金丝雀通过后，在 50% 流量进行 A/B 测试；若只是改进版本，可直接在金丝雀通过后切换到 100%。

### 记忆关键数字

- 金丝雀进度：1% → 10% → 25% → 50% → 75% → 100%
- 非确定性上限：相同输入多次运行间准确率波动达 15%
- 五大金丝雀指标：延迟、成本、错误/拒绝、输出长度、用户反馈
- 成本闸门：超过基线 20% 视为违例
- 回滚：秒级完成，不是小时

## 术语表

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| Shadow mode | “复制到新模型” | 零影响发送给候选模型用于日志记录 |
| Canary | “渐进流量” | 逐步暴露给用户的发布带有闸门 |
| Gates | “发布检查” | 阻止进一步发布的指标阈值 |
| Non-determinism | “LLM 方差” | 不可消除的运行间差异 |
| Policy flag | “标志翻转回滚” | 配置级别回滚，秒级完成 |
| Model pin | “注册表摘要” | 不可变的模型版本引用 |
| Argo Rollouts | “K8s 渐进” | Kubernetes 原生金丝雀/回滚控制器 |
| KServe | “推理 K8s” | 具备金丝雀特性的模型服务 |
| Istio weighted | “网格分流” | 服务网格流量拆分器 |
