# 工具使用和函数调用

> Toolformer（Schick 等，2023）开启了自监督工具标注。Berkeley Function Calling Leaderboard V4（Patil 等，2025）设立了2026年的目标：40% 智能体化，30% 多轮，10% 实时，10% 非实时，10% 幻觉检测。单轮已解决。记忆、动态决策和长周期工具链尚未解决。

**类型：** 构建  
**语言：** Python（标准库）  
**先决条件：** 第14阶段 · 01（智能体循环），第13阶段 · 01（函数调用深度解析）  
**时间：** ~60分钟

## 学习目标

- 解释 Toolformer 的自监督训练信号：仅当执行减少下一个词元损失时保留工具标注。
- 列出 BFCL V4 的五个评估类别及各自测量内容。
- 实现一个带有模式验证、参数强制转换和执行沙箱的标准库工具注册表。
- 诊断2026年开放的三个问题：长周期工具链、动态决策和记忆。

## 问题

早期工具使用关注：模型能否预测正确的函数调用？现代工具使用关注：模型能否跨40步链式使用工具，带有记忆、部分可观测性、从工具失败中恢复，并且不会虚构不存在的工具？

Toolformer 设定了基线：模型可以通过自监督学习何时调用工具。BFCL V4 定义了2026年的评估目标。两者之间的差距即是生产智能体所处的空间。

## 概念

### Toolformer（Schick 等，NeurIPS 2023）

思路：让模型为其预训练语料标注候选 API 调用。对于每个候选调用，执行它。仅当工具输出减少下一个词元损失时保留该标注。然后用过滤后的语料微调模型。

涉及工具：计算器、问答系统、搜索引擎、翻译器、日历。自监督信号纯粹基于工具是否帮助预测文本——无人工标签。

规模结果：工具使用随规模出现。小模型受工具标注影响负面；大模型获益显著。这就是为什么2026年前沿模型内嵌强工具使用，而大多数7B模型需显式微调工具使用才能可靠。

### Berkeley Function Calling Leaderboard V4（Patil 等，ICML 2025）

BFCL 是2026年事实上的评测标准。V4组成：

- **智能体化（40%）** — 全流程智能体轨迹：记忆、多轮、动态决策。
- **多轮（30%）** — 带工具链的交互式对话。
- **实时（10%）** — 用户提交的真实提示（更难分布）。
- **非实时（10%）** — 合成测试用例。
- **幻觉（10%）** — 检测不应调用任何工具的情况。

V3 引入了基于状态的评估：工具序列结束后，检查 API 实际状态（例如“文件是否创建？”），而非匹配工具调用的抽象语法树（AST）。V4 新增了网页搜索、记忆和格式敏感度类别。

2026年关键发现：单轮函数调用几近解决。失败集中在记忆（跨轮 Carry 上下文）、动态决策（基于前后结果选工具）、长周期链（20步以上出现漂移）和幻觉检测（无合适工具时拒绝调用）。

### 工具模式

每个提供者有一套模式。细节不同但结构一致：

```text
name: string
description: string（功能说明、何时使用）
input_schema: JSON Schema（属性、必需字段、类型、枚举）
```

Anthropic 直接使用 `input_schema`。OpenAI 使用 `function.parameters`。皆接受 JSON Schema。描述至关重要——模型读取它们以选择正确工具。错误的工具描述是错误选择工具的第一大根因。

### 参数验证

不信任任何工具调用。验证步骤：

1. **类型强制转换。** 模型可能返回字符串 "5"，而模式要求 int。若明确可转则强制转换；否则拒绝。
2. **枚举验证。** 若模式规定 `status in {"open", "closed"}`，模型返回 `"in_progress"`，则拒绝并返回具体错误。
3. **必填字段。** 缺少必填字段 -> 立即返回错误观察给模型，而非崩溃。
4. **格式验证。** 日期、邮箱、URL —— 用具体解析器验证，不用正则。

每个验证失败都应返回结构化观察，让模型可根据正确格式重试。

### 并行工具调用

现代服务支持同一助理轮次中并行调用多个工具。流程：

1. 模型发出3个带不同 `tool_use_id` 的工具调用。
2. 运行时执行它们（若无依赖则并行）。
3. 每个结果作为 `tool_result` 块回传，关联对应 `tool_use_id`。

工程规约：将关联 ID 视为关键字。若交换它们，结果将错配工具。

### 沙箱机制

工具执行即沙箱边界。详见第09课。简言之：每个工具应指定读写权限、网络访问、超时和内存限制。通用的 `run_shell(cmd)` 是红旗信号；具体的 `git_status()` 更安全。

## 构建它

`code/main.py` 实现了生产级工具注册表：

- JSON Schema 子集验证器（仅标准库）。
- 工具注册：含描述、输入模式、超时和执行器。
- 参数强制转换与枚举验证。
- 支持带关联 ID 的并行工具调度。
- 错误观察以结构化字符串形式返回。

运行：

```text
python3 code/main.py
```

追踪显示一个迷你智能体在一轮内调用三工具，其中一个故意传入格式错误，被模型可操作的具体错误拒绝。

## 使用它

每个提供者有自己的工具模式——Anthropic、OpenAI、Gemini、Bedrock。如需多提供者支持，使用翻译层（OpenAI Agents SDK、Vercel AI SDK、LangChain 工具适配器）。BFCL 是参考基准——若工具使用是产品核心，发布前务必用它测试智能体。

## 发布它

`outputs/skill-tool-registry.md` 生成针对特定任务域的工具目录、模式和注册表。包括描述质量检查（每个工具描述是否告诉模型何时使用？）。

## 练习

1. 添加一个 “无操作” 工具，让模型明确拒绝使用其他工具。在类似 BFCL 幻觉测试上评估效果。
2. 实现 int 作为字符串和 float 作为字符串的参数强制转换。强制转换在哪儿开始掩盖真实 bug？
3. 添加每个工具的超时和断路器（连续失败3次后60秒内拒绝调用）。这如何改变模型的恢复表现？
4. 阅读 BFCL V4 描述。选一个类别（例如“多轮”），用10个示例提示测试您的智能体。报告通过率。
5. 将标准库验证器移植至 Pydantic 或 Zod。Pydantic/Zod 捕获了玩具验证器未检测到的什么问题？
