# 编排模式：Supervisor（监督者）、Swarm（群体）、Hierarchical（分层）

> 在2026年框架中反复出现的四种编排模式：supervisor-worker（监督者-工人）、swarm / peer-to-peer（群体 / 点对点）、hierarchical（分层）、debate（辩论）。Anthropic（Anthropic公司）的指导原则是：“构建适合您需求的正确系统。” 从简单开始；只有当单一智能体加五种工作流模式不足时再考虑拓扑结构。

**类型：** 学习 + 构建  
**语言：** Python（标准库）  
**先决条件：** 第14阶段 · 12（工作流模式），第14阶段 · 25（多智能体辩论）  
**时间：** ~60分钟

## 学习目标

- 说出四种反复出现的编排模式及其适用场景。
- 描述2026年LangChain推荐的基于工具调用的监督与监督者库的区别。
- 解释Anthropic的“构建正确系统”规则及其如何影响拓扑选择。
- 使用标准库针对通用脚本化的LLM实现全部四种模式。

## 问题

团队往往在未必需要之前就开始使用“多智能体”。四种模式在各框架中反复出现；一旦能说出它们，就可以选择合适的模式——或直接跳过拓扑结构。

## 概念

### Supervisor-worker（监督者-工人）

- 中央路由LLM分派任务给专业智能体。
- 决定：循环回自身、交给专家或终止。
- 专家之间不直接通信，所有路由都通过监督者。

框架示例：LangGraph `create_supervisor`，Anthropic orchestrator-workers，CrewAI Hierarchical Process。

**2026年LangChain推荐：** 通过直接工具调用进行监督，而非使用 `create_supervisor`。给予更细粒度的上下文工程控制——你精确决定每个专家看到什么。

### Swarm / peer-to-peer（群体 / 点对点）

- 智能体通过共享工具界面直接交接。
- 无中央路由器。
- 相对于监督者延迟更低（跳数更少）。
- 更难推理（无单点控制）。

框架示例：LangGraph群体拓扑、OpenAI Agents SDK的交接（当所有智能体可相互交接时）。

### Hierarchical（分层）

- 监督者管理次级监督者，次级监督者管理工人。
- 在LangGraph中实现为嵌套子图；CrewAI中为嵌套团队。
- 能扩展到大规模智能体群体，但增加运维复杂度。

适用场景：当单一监督者的上下文预算不足以容纳所有专家描述时。

### Debate（辩论）

- 并行提议者 + 迭代交叉批判（第25课）。
- 严格来说不属于编排，更偏向验证，但在框架中表现为一种拓扑选择。

### CrewAI Crew 与 Flow

CrewAI形式化了两种部署模式：

- **Flow**，用于确定性的事件驱动自动化（推荐的生产起点）。
- **Crew**，用于自主的基于角色的协作。

这与上述四种模式正交，但与拓扑匹配：Flow通常是监督者或分层；Crew通常是具有LLM路由的监督者。

### Anthropic的指导原则

“LLM领域的成功不在于构建最复杂的系统，而在于为您的需求构建正确的系统。”

决策顺序：

1. 单一智能体 + 工作流模式（第12课）——从这里开始。
2. 监督者-工人模式——当有2-4个专家时。
3. 群体模式——当延迟比推理清晰度更重要时。
4. 分层模式——仅当监督者的上下文预算不足时。
5. 辩论模式——当准确性比成本重要时。

### 模式失败的典型原因

- **先入为主的拓扑思维。** “我们需要多智能体”，却没有明确多智能体要解决什么问题。
- **群体模式中的交接反弹。** A -> B -> A -> B。使用跳数计数器控制。
- **伪分层。** 三层结构因为“企业需求”；实际上只有两支团队。应合并。

## 构建

`code/main.py` 使用标准库针对脚本化LLM实现全部四种模式：

- `Supervisor` —— 中央路由器。
- `Swarm` —— 具有直接交接的点对点。
- `Hierarchical` —— 监督者的监督者。
- `Debate` —— 并行提议者 + 批判。

每种模式处理相同的三种意图任务（退款 / 错误 / 销售）。追踪形状不同。

运行：

```text
python3 code/main.py
```

输出：每个模式的追踪 + 操作计数。监督者最简洁；群体最短；分层最深；辩论最耗费。

## 使用

- **LangGraph** 用于监督者和分层（嵌套子图）。
- **OpenAI Agents SDK** 用于工具方式的交接（监督者形状）。
- **CrewAI Flow** 用于生产确定性工作流。
- **自定义** 用于辩论或需要精确控制时。

## 练习

1. 通过移除路由器将监督者-工人转换为群体。会出现什么问题？什么会变好？
2. 给群体添加跳数计数器：超过3次交接即拒绝。是否能捕获A->B->A的反弹？
3. 为12个专家领域构建两层分层系统。没有嵌套时上下文预算在哪失败？
4. 对四种模式使用生产性质的工作负载进行性能分析。哪种模式在哪些指标（延迟、成本、准确性、调试性）上表现最好？

## 关键词

| 术语                     | 普通定义           | 实际含义                                      |
|--------------------------|--------------------|-----------------------------------------------|
| Supervisor-worker（监督者-工人） | “路由 + 专家”       | 中央LLM分派专家；专家间不直接通信              |
| Swarm（群体）              | “点对点”           | 通过共享工具直接交接；无中央路由器               |
| Hierarchical（分层）       | “监督者的监督者”   | 嵌套子图用于大规模群体                          |
| Debate（辩论）             | “提议者 + 批判”     | 并行提议者，交叉批判（第25课）                   |
| Tool-call-based supervision（基于工具调用的监督） | “无库的监督者”    | 将监督者实现为直接的工具调用以控制上下文           |
| Crew（团队）               | “自治团队”         | CrewAI基于角色的协作模式                         |
| Flow（流程）               | “确定性工作流”     | CrewAI事件驱动的生产模式                         |
