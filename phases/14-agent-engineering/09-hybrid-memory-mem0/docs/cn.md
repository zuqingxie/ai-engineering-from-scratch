# Hybrid Memory: Vector + Graph + KV（混合内存：向量+图+键值）（Mem0）

> Mem0（Chhikara 等，2025）将内存视为三个并行存储——向量用于语义相似性，KV 用于快速事实查找，图用于实体关系推理。检索时由评分层融合这三者。这是2026年外部内存的生产标准。

**类型：** 构建  
**语言：** Python（标准库）  
**先决条件：** 第14阶段 · 07（MemGPT），第14阶段 · 08（Letta Blocks）  
**时长：** 约75分钟

## 学习目标

- 解释为何单一存储（仅向量、仅图、仅KV）不足以支持智能体内存。
- 说出 Mem0 的三种并行存储及它们各自优化的内容。
- 描述 Mem0 的融合评分——相关性、重要性、时效性——以及为何是加权求和而非层级结构。
- 用标准库实现一个玩具版三存储内存，带有一个写入所有三者的 `add()` 和一个融合结果的 `search()`。

## 问题

单个存储对以下三类查询之一总是不合适：

- **语义相似性**——“我们上周讨论过哪些有关智能体漂移的话题？”向量存储胜出；KV 和图存储会遗漏。
- **事实查找**——“用户的电话号码是多少？”KV 存储胜出；向量存储浪费，图存储过度设计。
- **关系推理**——“哪些客户共享同一账单实体？”图存储胜出；向量和KV无法回答。

生产环境中的智能体在一次会话里会提出这三类查询。单一存储内存总会在其中两个类别出现错误。Mem0 的贡献是将三者统一放在单一的 `add`/`search` 接口后端，用评分函数融合结果。

## 概念

### 三存储并行

Mem0（arXiv:2504.19413，2025年4月）在调用 `add(text, user_id, metadata)` 时：

1. 从文本中提取候选事实（由大语言模型驱动的步骤）。
2. 将每个事实写入向量存储（embedding）以支持语义搜索。
3. 将每个事实写入以 `(user_id, fact_type, entity)` 为键的KV存储，以实现O(1)查找。
4. 将每个事实写入图存储（Mem0g）作为带类型的边，用于关系查询。

调用 `search(query, user_id)` 时：

1. 向量存储返回按embedding余弦相似度排名的top-k结果。
2. KV存储返回基于查询推导出的 `(user_id, type, entity)` 的直接匹配项。
3. 图存储返回从查询实体可达的子图。
4. 评分层融合这三者结果。

### 融合评分

```text
score = w_relevance * relevance(q, record)
      + w_importance * importance(record)
      + w_recency * recency(record)
```

- **相关性** — 向量余弦相似度，KV 精确匹配，图路径权重。
- **重要性** — 写入时标签或学习得出（某些事实更重要：名字、ID、政策等）。
- **时效性** — 自上次写入或读取时间起的指数衰减。

权重根据产品调整。聊天智能体提高 `w_recency`；合规智能体提高 `w_importance`；检索智能体提高 `w_relevance`。

### Mem0g 与时间推理

Mem0g 增加了冲突检测器。当新事实与已有边矛盾时，标记已有边为无效但不删除。时间查询（“用户三月时的城市是哪里？”）遍历特定时间点有效的子图。

这正是 Letta 的失效模式泛化出的合规级行为。

### 基准数据

Mem0 论文报告（2025）：

- **LoCoMo**（长对话记忆）：91.6  
- **LongMemEval**（长时记忆评测）：93.4  
- **BEAM 1M**（百万令牌内存基准）：64.1  

比较基线（全上下文128k LLM，扁平向量存储，扁平KV存储）均低10分以上。单看基准不决定选择，操作形态才关键，但结果表明融合设计非小数目误差。

### 范围分类法

Mem0 按范围划分内存：

- **用户内存** — 跨会话持久，基于 `user_id` 索引。
- **会话内存** — 同一线程内持久。
- **智能体内存** — 每个智能体实例状态。

每次写入选定一个范围。检索可跨范围查询，并可针对每个范围赋权。不经意混合范围是导致“助理告诉Alice关于Bob项目”的事故根源。

### 该模式的问题点

- **Embedding漂移。** 前一百条查询看似正确的向量结果随着语料增长而退化。需定期重新嵌入最常用的top-N记录。
- **KV模式膨胀。** `(user_id, type, entity)`看似简单，实际每个团队都会扩展自己的`type`。需季度审计类型集。
- **图爆炸。** 一个嘈杂的抽取器每条消息产生50条边。限制每次`add`调用的图写入；丢弃低置信边。

## 构建它

`code/main.py` 实现了标准库中的三存储模式：

- `VectorStore` — 使用简单的token重叠相似度代替embedding。
- `KVStore` — 基于 `(user_id, fact_type, entity)` 的字典。
- `GraphStore` — 带类型的边 (subject, relation, object, valid)。
- `Mem0` — 顶层门面，提供 `add()`、`search()`、融合评分、范围感知检索。
- 包含一个多用户多会话对话的完整执行跟踪。

运行：

```text
python3 code/main.py
```

输出显示三个独立的召回路径及融合后的top-k。修改 `main()` 顶部的评分权重，观察排名变化。

## 使用它

- **Mem0（Apache 2.0）** — 生产就绪。可自托管 Postgres + Qdrant + Neo4j，或使用托管云。
- **Letta** — 三层设计：核心/召回/归档；可自选向量与图后端。
- **Zep** — 商业方案，带时间知识图与事实抽取。
- **自定义构建** — 当需要精确控制抽取器（合规）或融合权重（语音智能体时效性优先）时。

## 练习

1. 用真实嵌入模型（sentence-transformers、Ollama、OpenAI embeddings）替换玩具向量相似度。测试合成长对话的 recall@10。写入1000次后排名是否漂移？
2. 添加时间查询接口：`search(query, as_of=timestamp)`。仅返回该时间点或之前有效的记录。哪个存储需要最多修改？
3. 实现冲突检测器：若新事实与图边冲突，使旧边失效并记录二者。测试案例：“用户居住在柏林”->“用户居住在里斯本”。
4. 将融合评分扩展为包含 `user_feedback` 维度（检索记录点赞）。如何防止“作弊”（智能体只返回之前获赞的记录）？
5. 阅读 Mem0 文档（`docs.mem0.ai`），将玩具实现移植到 `mem0` 客户端调用上。对同20条测试查询比较检索质量。
