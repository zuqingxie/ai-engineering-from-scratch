# 长时间运行的后台代理：持久化执行（Durable Execution）

> 生产环境中的长周期代理不会运行在 `while True` 循环中。每一次 LLM 调用都作为一个带有检查点（checkpoint）、重试（retry）和重放（replay）的活动（activity）。Temporal 的 OpenAI Agents SDK 集成于 2026 年 3 月正式发布。Claude Code Routines（Anthropic）运行预定的 Claude Code 调用，而无需持久的本地进程。会话在人工输入时暂停，能跨部署保存状态，并从由 `thread_id` 作为键的最新检查点恢复。新的人机交互体验背后是一个老模式——工作流编排（workflow orchestration）——并带来一个新输入：LLM 调用作为非确定性活动，必须在恢复时确定性重放。

**类型：** 学习  
**语言：** Python（标准库，最小持久化执行状态机）  
**前提条件：** 第 15 阶段 · 10（权限模式）、第 15 阶段 · 01（长周期代理）  
**时间：** 约 60 分钟

## 问题描述

考虑一个运行四小时的代理。它调用了三个工具，向用户提示两次，并进行了四十次 LLM 调用。过程中宿主机重启了。会发生什么？

- 在天真的 `while True` 循环中：所有进度丢失。运行从头开始重启。三个有真实副作用的工具调用再次执行。用户被重复提示已经批准的内容。四十次 LLM 调用被重新计费。
- 使用持久化执行：运行从最新检查点恢复。已完成的活动不再重复执行；它们的结果从持久化日志中重放。用户不必重新批准已批准的内容。已完成的 LLM 调用不再重新计费。

这与工作流引擎（如 Temporal、Cadence、Uber 的 Cherami）十年来推出的模式相同。新的地方是 LLM 调用现在成为了一种活动——非确定性、昂贵、有副作用——且它们完美符合该模式。

本课主线：长周期的可靠性会衰减（METR 观察到约“35分钟降级”——成功率随周期大致呈二次下降）。持久化执行使运行时长超过可靠性阈值成为可能。这是一种新型的安全失败方式（设计正确时）或不安全失败（设计错误时）。

## 概念详解

### 活动（Activities）、工作流（Workflows）与重放（Replay）

- **工作流（Workflow）**：确定性的编排代码。定义活动顺序、分支与等待。必须是确定性的，以便能从事件日志中重放时没有意外差异。
- **活动（Activity）**：非确定性、可能失败的工作单元。LLM 调用、工具调用、文件写入、HTTP 请求等。每个活动的输入和（完成后）输出都会被记录。
- **事件日志（Event log）**：持久化的存储。记录每个活动的开始、完成、失败、重试和工作流的每个决策。
- **重放（Replay）**：恢复时，工作流代码从头重新运行；已完成的活动直接返回日志中的结果，无需重新执行。只有未完成的活动才实际运行。

这类似 React 针对虚拟 DOM 的重新渲染，或 Git 从提交构建工作树。编排器的确定性保证了持久化成本低廉。

### 为什么 LLM 调用符合该模式

LLM 调用具有以下特征：

- 非确定性（温度 > 0；即使温度为 0，不同模型版本间结果也会漂移）。
- 昂贵（金钱与延迟）。
- 可能失败（速率限制、超时）。
- 具有副作用（如果调用工具）。

这正是活动的典型特性。将每个 LLM 调用包装为活动，您就拥有了指数退避的重试、跨重启的检查点，以及可用于调试的可重放轨迹。

### 以 `thread_id` 作为检查点键

LangGraph、Microsoft Agent Framework、Cloudflare Durable Objects 和 Claude Code Routines 都趋同于同一 API 形态：`thread_id`（或等价标识）标识会话；每次状态变更持久化到后端（PostgreSQL 默认，开发时用 SQLite，缓存用 Redis）；恢复时读取最新检查点。

不同后端的特点：

- **PostgreSQL**：持久、支持查询、能跨部署存活。LangGraph 默认后端。
- **SQLite**：仅限本地开发，跨主机数据丢失。
- **Redis**：速度快，但除非配置了 AOF/快照，否则数据易失。
- **Cloudflare Durable Objects**：透明分布式；通过唯一键作用域；存活时间从几小时到几周。

### 人工输入作为一级状态

提议-然后提交（第 15 课）要求持久化“等待人工”状态。工作流暂停，外部队列持有挂起请求，待审批后准确从该点恢复。无持久化时只能是尽力而为；有了持久化，则晚上审批，早上继续执行。

### 35 分钟降级

METR 观察到每类代理在连续运行约 35 分钟之后可靠性显著衰减。任务时间翻倍，失败率大约增加四倍。持久化执行不解决这个问题，但允许长时间运行超过可靠性极限。安全做法是结合持久化与需人工干预的检查点，并配合预算终止开关（第 13 课），限定总算力消耗，无论墙钟时间。

### 何时不适用持久化执行

- 运行时间不到几分钟且无人工输入的任务。开销大于收益。
- 纯只读信息检索。
- 需要在单一上下文窗口内端到端正确性保障的任务（某些推理任务、一-shot 生成等）。

## 使用方法

`code/main.py` 实现了一个基于 Python 标准库的最小持久化执行引擎。支持：

- `@activity` 装饰器，向 JSON 事件日志记录输入和输出。
- 一个顺序调度活动的工作流函数。
- `run_or_replay(workflow, event_log)` 函数，重放已完成活动而不重新执行。

驱动器模拟一个三活动的工作流，中途崩溃，并展示了 (a) 天真重试重新执行所有操作与 (b) 重放只执行缺失活动的不同。

## 练习

1. 运行 `code/main.py`。观察天真重试与重放的活动执行次数差异。改变崩溃点，验证重放次数相应变化。

2. 修改玩具引擎，显式使用 `thread_id`。模拟两个并发会话共享引擎，确认各自事件日志不会冲突。

3. 选取玩具引擎中的一个活动，加入非确定性（例如在工作流决策中插入真实时间戳）。展示重放时的差异。解释真实引擎如何处理（副作用注册、`Workflow.now()` API 等）。

4. 阅读 LangChain 的《生产深度代理背后的运行时》文章。列出运行时持久化的所有状态及其对应的故障模式。

5. 为持续 6 小时的自动化编码任务设计检查点策略。在哪些时刻做检查点？崩溃后如何恢复？哪些部分需重新人工干预？

## 关键词汇

| 术语 | 通俗说法 | 实际含义 |
|---|---|---|
| Workflow（工作流） | “代理脚本” | 确定性编排代码；可从事件日志重放 |
| Activity（活动） | “一步” | 非确定性单元（LLM、工具调用）；执行前后被记录 |
| Event log（事件日志） | “后端存储” | 每个状态变更的持久记录 |
| Replay（重放） | “恢复” | 重新运行工作流；已完成活动直接返回日志结果，无需重复执行 |
| Checkpoint（检查点） | “保存点” | 以 `thread_id` 为键的持久化状态；恢复时最新数据生效 |
| thread_id | “会话键” | 标识持久状态的会话标识符 |
| 35-minute degradation（35 分钟降级） | “可靠性衰减” | METR：成功率随时间近似二次下降 |
| Non-determinism（非确定性） | “重放漂移” | 实时时钟、随机数、LLM 输出；需注册为副作用 |
