# 检查点与回滚

> 每个图状态（graph-state）转换都会被持久化。当一个 worker 崩溃时，其租约（lease）会过期，另一个 worker 会从最新的检查点继续执行。Cloudflare Durable Objects 可以跨小时或数周持有状态。Propose-then-commit（第15课）为每个动作定义回滚计划。动作后验证（post-action verification）闭环控制。欧盟 AI 法案第14条（EU AI Act Article 14）要求对高风险系统实施有效的人类监督——实际上这意味着检查点必须可查询，回滚必须进行演练，审计轨迹必须在部署后依然存在。严峻的失败模式是：没有幂等键（idempotency keys）和前置条件检查时，重试可能会对已经批准的动作执行二次。动作后验证能够捕捉此类问题。

**类型：** 学习  
**语言：** Python（标准库，检查点和回滚状态机）  
**先决条件：** 第15阶段·12课（持久执行 Durable execution）、第15阶段·15课（Propose-then-commit）  
**时间：** 约60分钟

## 问题描述

持久执行（第12课）使被崩溃的代理可恢复执行。Propose-then-commit（第15课）使已批准的动作可审计。本课将两者结合：当一项已批准的动作部分执行后崩溃并恢复时，会发生什么？回滚何时执行，针对哪个状态？

实际系统的连接方式不同：

- **LangGraph** 在 PostgreSQL 中为每个图状态转换设置检查点。worker 崩溃时，租约释放，另一个 worker 从最新检查点恢复。工作流程会在 `interrupt()` 处暂停，该操作本身也被持久化。
- **Cloudflare Durable Objects** 跨小时或数周保存每个键的状态。将计算与存储（针对已批准动作）共置。
- **Microsoft Agent Framework** 在工作流 API 中暴露 `Checkpoint` 原语；重放加幂等性覆盖重试情况。

在所有情况下，真正奏效的组合是：幂等键（防止二次执行）+ 前置条件检查（状态仍符合批准时的情况）+ 动作后验证（确认副作用确实发生）+ 验证失败时的回滚。

## 概念

### 每一步转换都持久化

图状态转换是将工作流从一个命名状态变更到另一个命名状态的任何步骤。简单实现只在特定提交点持久化；生产实现则在每次转换时持久化。这个代价（额外的写入操作）相对于可靠性的提升（可随时重放，租约恢复精确）来说很小。

### 租约恢复

worker 崩溃时，工作流不会丢失；租约（worker 执行该运行的短期认领）会过期。另一个 worker 会接手最新的检查点并恢复流程。租约机制使生产系统能在滚动部署时不丢失正在执行的工作。

### 幂等性加前置条件

单纯幂等性不够。举例：工作流被批准执行“当账户余额大于 1000 美元时，从 A 转账 100 美元给 B”。工作流提交执行，过程中崩溃，恢复了。如果只验证幂等键，执行会正确运行一次。但考虑崩溃到恢复的间隙，A 的余额因其他工作流变为 500 美元。幂等检查依然通过，但前置条件不满足。没做前置条件检查，则会导致透支。

每个关键动作都需要两者：

- **幂等键**：防止重复执行。  
- **前置条件检查**：确认状态仍与批准时一致。

### 动作后验证

“工具返回200”不等于验证。真正的验证是重新读取目标状态，确认副作用实际发生。常用模式：

- 数据库更新：`UPDATE ... RETURNING *` 再断言返回行与预期一致。  
- 邮件发送：检查发送箱中是否有对应的消息 ID。  
- 文件写入：读取回文件并校验哈希。  
- API 调用：随后对目标资源执行 `GET`。

验证失败时，工作流处于已知错误状态，此时启动回滚。

### 回滚计划

Propose-then-commit（第15课）中，每个关键动作都带有回滚计划。类型包括：

- **带内回滚（In-band rollback）**：直接逆转副作用（如对 `INSERT` 操作执行 `DELETE`，发送纠正邮件等）。  
- **补偿事务（Compensating transaction）**：新动作中和原动作（常见的 SAGA 模式）。  
- **带外回滚（Out-of-band rollback）**：提醒人工，暂停工作流，留存错误状态供调查。

不执行操作的回滚（“我们无法撤销此操作”）必须在提议中注明。没有回滚的动作在提交时需要更高强度的人工监督（第15课的挑战与应答机制）。

### 欧盟 AI 法案第14条的操作解读

第14条对高风险系统要求“有效的人类监督”。从操作角度理解，即：

- 审计人员可以查询检查点。  
- 回滚已演练（至少一次端到端测试）。  
- 审计轨迹在部署后依然存在（检查点后端非短暂存储）。  
- 失败的验证触发警报而非静默记录。

工作流如果在提交时崩溃、恢复、完成副作用但缺少验证+回滚路径，则无法通过第14条的检验。

### 严重失败模式：双重执行

此领域最常见生产事故流程：

1. 动作获批，分配幂等键 k。  
2. 开始提交，执行成功，返回 200。  
3. 工作流崩溃，未持久化“已提交”状态。  
4. 恢复时，看到“已批准但未提交”，再次执行。  
5. 副作用执行两次。

缓解方案：在执行前持久化“进行中”意图，执行时绑定幂等键，后通过动作后验证成功后才标记“已提交”。如果动作成功但状态写入失败，待验证后必要时重试。如果状态写入成功但动作失败，恢复时通过验证确保仅执行一次。

## 练习

1. 运行 `code/main.py`。验证四种场景。对“提交中崩溃”的场景，确认动作在重试时仅触发一次。  
2. 修改“先标记完成再执行”模式，使状态写入发生在动作之后。重新运行崩溃场景，测量重复动作次数。  
3. 为具体的生产动作设计回滚计划（例如“向 Slack 频道发消息”），分类为带内、补偿或带外回滚，说明理由。  
4. 选取你熟悉的工作流，识别所有状态转换。标明每个状态转换持久化需求（持久化/不持久化），统计未持久化的转换。  
5. 回滚演练测试：设计一个端到端测试，执行真实工作流，制造崩溃，并确认回滚路径触发。测试应断言哪些内容？

## 关键词

| 术语 | 常用说法 | 实际含义 |
|---|---|---|
| Checkpoint | “保存点” | 每个图状态转换持久化到持久存储 |
| Lease | “worker 认领” | 短期认领，表示 worker 正在执行，崩溃即过期 |
| Precondition | “状态门控” | 断言状态仍符合批准动作时的条件 |
| Post-action verify | “重读检查” | 确认副作用实际发生于目标系统 |
| In-band rollback | “直接撤销” | 通过逆向操作撤销副作用 |
| Compensating transaction | “SAGA 撤销” | 新动作中和原动作的影响 |
| Mark-as-done-first | “状态写入顺序” | 在提交返回前持久化已提交状态 |
| Article 14 | “欧盟 AI 法案人类监督” | 操作性要求：检查点可查询、回滚演练、审计轨迹可审 |
