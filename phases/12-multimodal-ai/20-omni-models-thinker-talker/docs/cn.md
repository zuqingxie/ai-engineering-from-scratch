# 全能模型（Omni Models）：Qwen2.5-Omni 与思考者-讲话者（Thinker-Talker）分离

> GPT-4o 于2024年5月的产品演示造成了冲击，原因不在于底层模型，而在于产品形态——一个语音接口，你讲话，模型看到摄像头所见，并在250毫秒内用语音回应。开放生态系统在2024年和2025年余下时间竞相达成这一产品体验。Qwen2.5-Omni（2025年3月）是参考的开放设计：一个思考者（大型文本生成 transformer）加一个讲话者（并行语音生成 transformer），通过流式语音 token 连接。Mini-Omni 简化了它，Moshi 达到相同延迟，GLM-4-Voice 拓展到中文。本课解读思考者-讲话者架构及使流式实时对话可行的延迟预算。

**类型：** 构建  
**语言：** Python（标准库，流式流水线延迟模拟器 + VAD 循环）  
**先修课：** 阶段 12 · 19（音频 LLM）、阶段 12 · 16（任意到任意）  
**时长：** ~180 分钟

## 学习目标

- 将推理流水线拆分为思考者（文本推理）和讲话者（语音合成），并解释为何并行流式有效。  
- 计算对话交互的首音字节时间（TTFAB）预算，逐组件分析。  
- 描述 TMRoPE 在思考者中的跨视觉、音频和文本的时间对齐位置编码。  
- 说出三种实时对话模式：半双工、轮流发言、全双工。

## 问题描述

一个实时语音助理必须快速完成许多任务：

1. 听用户说话。实时语音分词，语音活动检测（VAD）判断何时说完。  
2. 可选地“看”，摄像头输入以 2-4 FPS 流方式送入思考者，与音频共同处理。  
3. 思考。基于对话历史构造回复。  
4. 讲话。生成音频 token，解码为波形，流式传输到用户扬声器。

每步都会带来延迟。良好的对话体验需要总往返时间 <500毫秒——低于此，用户不会察觉延迟。GPT-4o 号称 ~250 毫秒，Moshi 约 160 毫秒，Qwen2.5-Omni 在 350-500 毫秒之间。

每个组件必须支持流式。绝不能“先批量全部处理再解码”。

## 概念解析

### 思考者（Thinker）与讲话者（Talker）

Qwen2.5-Omni 的架构拆分：

- 思考者：一个7B到80B规模的文本生成 transformer。输入交织的文本 + 图像 + 音频 token，输出表示要说内容的文本 token。  
- 讲话者：一个较小的语音生成 transformer（200M-1B），消耗思考者的文本输出 token 加上最近的语音上下文 token，生成离散语音 token（残差向量量化索引）。  
- 语音解码器：流式波形解码器（SNAC，MoVQGAN 家族）实时将语音 token 解码成音频样本。

这种分离至关重要。思考者必须大以进行良好推理。讲话者可小，因为其任务局部——将文本转为语音 token。更大的讲话者并不更有表现力，反而更慢。

两者并行运行：

1. 思考者输出文本 token t_i。  
2. 讲话者消费流式传入的 t_i，发出语音 token s_i、s_{i+1}、…、s_{i+k}。  
3. 语音解码器边接收语音 token 边输出音频样本。  
4. 当思考者处理到文本 token t_{i+3} 时，讲话者已经流出 t_0 到 t_{i+2} 的语音。

### TMRoPE —— 时间对齐的多模态位置编码

思考者需要整合图像帧（比如 4 FPS）、音频帧（50 帧/秒）和文本对话历史。朴素的顺序编码（先图像全序，后音频全序，再文本）会丢失时间对齐。

TMRoPE 为每个 token 分配绝对时间戳。视觉 token 时间为 2.3 秒，音频 token 时间为 2.32 秒，用户的文本“stop”时间为 2.35 秒。RoPE 根据时间戳旋转注意力，模型视这些为时间上并发。

这是“他挥手同时说‘你好’”能被理解的基础——模型在同一时刻看到视频帧和音频。

### 流式语音合成

语音 token 必须流式输出。Mini-Omni（谢霆锋 & 吴磊，2024）提出了“语言模型可以边听边说”的流式理念：思考者与讲话者的输出 token 交织在同一序列中。讲话者一旦思考者提交下一个文本 token 就开始发声。无批处理界限。

Moshi（Défossez 等，2024年10月）是最快开放实现，在 A100 上首音字节时间仅160毫秒。架构是单个7B模型，交替输出文本和语音 token，带有将思考流与讲话流分离的“内心独白”机制。实质上是将思考者+讲话者融合为一个模型并进行细致训练。

### VAD 与轮流发言

语音活动检测在输入端运行，两种机制：

- 半双工：用户说，模型听；模型说，用户听。通过 VAD 静默检测（约200毫秒）实现明确交接。  
- 全双工：双方可同时说话。模型可进行反馈式回应（“嗯哼”）或打断，更复杂。Moshi 支持该方式。

Qwen2.5-Omni 默认支持半双工，通过静默阈值实现轮流发言。全双工需应用层处理。

### Qwen3-Omni（2025年11月）

继任版本。Qwen3-80B思考者，更大讲话者，改进版本的 TMRoPE-v2。延迟接近 GPT-4o 的250毫秒。开放权重。在OmniBench中对标 Gemini 2.0 Live。

### 生产级延迟预算

典型流式交互中：

- 麦克风到音频 token：40-80 毫秒。  
- 预填充（提示 + 历史）：7B约100-200毫秒，70B更久。  
- 思考者第一文本 token ：40 毫秒。  
- 讲话者处理第一文本 token ：20 毫秒。  
- 第一个语音 token 提交：40 毫秒。  
- 残差向量量化解码：30 毫秒。  
- 语音波形解码：50-80 毫秒。

7B 总计首音字节时间 320-510 毫秒，70B 则为 600-900 毫秒。前沿质量通常需要 70B+，因此存在延迟差距。

### token 速率计算

以16kHz语音和50Hz基频语音 token 计，每秒需50个语音 token 输出。讲话者必须保持≥50 tok/s 才能跟上。以典型 LLM 在 H100 上的 30-80 tok/s 吞吐量看，小型（200-300M）讲话者足够快，7B讲话者则会掉队。

这就是为什么存在小型专用讲话者模型的原因，而不是“仅用主模型”。

## 使用说明

`code/main.py` 文件：

- 模拟思考者-讲话者流水线，模拟 token 释放速率。  
- 计算可配置模型规模和麦克风采样率下的首音字节时间（TTFAB）。  
- 演示具有 VAD 静默阈值的半双工轮流发言。

## 部署

本课将生成 `outputs/skill-omni-streaming-budget.md`。给定实时语音产品的目标 TTFAB 和功能需求（视觉输入、双语、全双工），选择 Qwen2.5-Omni、Qwen3-Omni、Moshi 或 Mini-Omni，确定思考者/讲话者大小。

## 练习

1. 目标 TTFAB 为300毫秒。算出7B思考者和300M讲话者的每个组件延迟。  
2. Qwen2.5-Omni 使用 TMRoPE。描述模型在一个用户于 t=1秒开始说话，摄像头于 t=1.2秒捕捉到一个手势的提示中实际看到的情况。  
3. 全双工要求模型边听边说。设计一种训练数据格式以支持这种能力。  
4. 阅读 Moshi 论文第4节，描述“内心独白”分离机制及其为何避免思考者-讲话者分层。  
5. 计算吞吐预算：讲话者要多快发 token，才能满足16kHz语音每秒50个基本语音 token 的速率？

## 关键词

| 术语 | 常用说法 | 实际含义 |
|------|----------|----------|
| 思考者（Thinker） | “推理大脑” | 生成要说内容的大型文本生成 transformer |
| 讲话者（Talker） | “发声嘴巴” | 从思考者文本生成离散语音 token 的小型 transformer |
| TTFAB | “延迟预算” | 首音字节时间：用户说完到第一音频样本输出的时间 |
| TMRoPE | “时间对齐的RoPE” | 采用绝对时间戳跨视觉、音频、文本的位置编码 |
| 半双工（Half-duplex） | “轮流发言” | 用户与模型交替发言；VAD 静默检测用户结束 |
| 全双工（Full-duplex） | “同时发声” | 模型可同时听与说，支持反馈回应 |
| 内心独白（Inner monologue） | “Moshi 分离机制” | 单模型设计，思考流与讲话流交替输出 |
