# 并行 / 群集 / 网络架构

> 与 supervisor（监督者）对比：无中央决策者。代理读取共享事件总线，异步获取工作，写回结果。LangGraph 明确支持“Swarm Architecture（群集架构）”，用于去中心化、动态环境。Matrix（arXiv:2511.21686）将控制流和数据流都表示为通过分布式队列传递的序列化消息，消除协调者瓶颈。权衡明确：以确定性和可追溯性换取可扩展性。Swarm 适合许多独立子问题的任务；不适合需要单一连贯计划的任务。

**类型：** 学习 + 构建  
**语言：** Python（stdlib，`threading`，`queue`）  
**先决条件：** Phase 16 · 05（Supervisor Pattern），Phase 16 · 04（Primitive Model）  
**时长：** ~75 分钟

## 问题

Supervisor（监督者）能扩展到几个工作人员。那几百呢？监督者本身成为瓶颈：关于谁做什么的每一个决定都汇集到一个代理。一个缓慢的计划步骤就会阻塞整个系统。

Swarm 架构颠倒了设计。不是由中央计划者分发工作，而是工作人员从共享队列中挑选工作。“协调”内建于事件总线语义中。无协调者；系统可扩展直到队列成为瓶颈。

## 概念

### 结构图

```text
                ┌──── 共享队列 ────┐
                │                   │
       ┌────────┼────────┐  ◄──────┬───┘
       ▼        ▼        ▼         │
     Worker  Worker  Worker   Worker
      A       B       C        D
       │        │        │         │
       └────────┴────────┴─────────┘
                 │
                 ▼
            结果池
```

无协调者。每个工作人员重复以下操作：拉取任务、处理、写回结果（可选地入队后续任务）。

### 何时适用 Swarm

- **许多独立任务。** 爬取、转换、分类。任务之间互不依赖。
- **任务时长不固定。** 某些任务耗时 100ms，某些耗时 10s，Swarm 自动平衡负载——快的工作人员拉取更多作业。监督者必须预测时长。
- **重视吞吐量胜过确定性。** 关心总体完成时间，而非严格顺序。

### 何时不适用 Swarm

- **有序工作流。** 如果步骤 3 需要步骤 2 的输出，Swarm 风险是步骤 3 先于步骤 2 完成。
- **全局计划任务。** 复杂研究问题受益于规划者。群集的研究者产出独立事实，而非连贯报告。
- **调试困难。** 无中央日志，异步工作，复现缺陷代价高。

### Matrix（arXiv:2511.21686）

Matrix 是 2025 年论文，将群集推进到自然结论：控制流与数据流均为分布式队列上的序列化消息。无中央协调者。容错来自消息持久性。可扩展性由消息代理承担，而非系统本身。

贡献：一种编程模型，使多代理协调变成“该代理订阅哪个消息主题？”而非“监督者下一步选谁？”这令系统看起来像 pub/sub（发布/订阅）事件网格。

### LangGraph 的 Swarm Architecture

LangGraph 2025 文档明确描述“Swarm Architecture（群集架构）”作为多代理模式之一：代理是节点，边形成带环的有向图，且任何节点都可从池中激活。工作人员根据条件从可用工作中挑选，而非由监督者分配。

### 失败模式：饥饿和热点问题

如果所有工作人员都拉取最快的可用任务，长任务永远不被选中，直到只剩它们。典型的队列饥饿问题。

缓解措施：  
- 使用带显式老化的优先级队列（等待时间越长，优先级越高）。  
- 工作者专门化：部分工作人员只处理“长”任务。  
- 背压：限制进入队列的快任务数量。

### 基于内容的路由关联

Swarm 天然适合内容基路由（Lesson 22）。不是普通队列，而是为每种消息类型分配一个队列。专门工作人员只订阅自己类型队列。这是能扩展到数千代理的消息总线架构基础。

## 构建它

`code/main.py` 实现了 4 个工作线程的群集，从共享 `queue.Queue` 拉取任务。任务时长不一（有快有慢）。示例对比：

- **顺序基线：** 一个工作人员串行处理所有任务。  
- **固定分配：** 每个任务预分配给具体工作人员（监督者风格）。  
- **Swarm：** 工作人员从共享队列拉取任务。

Swarm 自动平衡负载；固定分配时，当分配的任务慢时，快速工作人员空闲。

运行：

```text
python3 code/main.py
```

输出显示每个工作人员的任务计数（Swarm 分配不均但最优）及总计时。

## 使用它

`outputs/skill-swarm-fit.md` 评估任务是否适用 Swarm 还是 Supervisor。输入：任务独立性、时长差异、顺序需求、调试需求。

## 发布它

清单：

- **带老化的优先级队列。** 防止长任务饥饿。  
- **工作人员幂等性。** 任务可能被多次拉取（中途崩溃重试）。工作者必须幂等。  
- **持久队列。** 生产环境使用 Kafka、Redis Streams 或数据库后端队列。`queue.Queue` 仅内存。  
- **每任务可观测性。** 每任务有 trace ID，工作人员用它记录开始/结束。  
- **背压。** 队列增长快于工作者处理时，减缓生产者。

## 练习

1. 运行 `code/main.py`。Swarm 在时长可变负载中比顺序快多少？比固定分配快多少？  
2. 添加优先级队列变体（用 `queue.PriorityQueue`），按任务“重要性”字段分配优先级。观察低优先级任务在持续负载下是否发生饥饿。  
3. 实现热点检测器：当任何工作人员处理的任务数是最慢工作人员的 3 倍时记录日志。这说明任务时长分布有什么特点？  
4. 阅读 Matrix 论文(arXiv:2511.21686)摘要和 3 节。指出 Matrix 接受的一个具体权衡（扩展性提升）和放弃的一个方面（可追溯性，确定性）。  
5. 将群集示例改造为使用存放 `(task_type, payload)` 元组的 `queue.Queue`，工作人员只订阅特定类型。当任务异质时，什么路由规则合理？

## 关键术语

| 术语 | 俗称 | 实际含义 |
|------|------|----------|
| Swarm architecture（群集架构） | “去中心化代理” | 工作人员从共享队列拉取任务，无中央协调者。 |
| Event bus（事件总线） | “代理订阅主题” | 消息代理按类型或内容将任务路由给工作人员。 |
| Starvation（饥饿） | “任务从不运行” | 因高优先级工作持续进入，低优先级任务从未被选中。 |
| Hot-spotting（热点问题） | “一个工作人员被淹没” | 负载不均，一个工作人员拿到大多数任务。 |
| Back-pressure（背压） | “减缓生产者” | 当队列趋满，向上游发出停止生产的信号。 |
| Idempotent worker（幂等工作者） | “安全重跑” | 同一任务重复处理结果相同。因工作人员可能中途崩溃。 |
| Durable queue（持久队列） | “崩溃不丢失” | 磁盘或复制存储支持的队列，工作人员崩溃任务不丢失。 |
| Matrix framework（Matrix 框架） | “全消息传递群集” | 控制流和数据流均为分布式队列上的序列化消息。 |
