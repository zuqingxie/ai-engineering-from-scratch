# 共享内存（Shared Memory）和黑板（Blackboard）模式

> 到2026年，多智能体系统并存两种方法：**消息池（message pool）**（每个人都能看到所有人的消息，如AutoGen GroupChat或MetaGPT）和**带订阅的黑板（blackboard with subscription）**（智能体订阅相关事件，如Context-Aware MCP或Matrix框架）。两者都是多智能体系统中唯一的有状态部分——也意味着两者是有趣的错误所在。参考的失败模式是**内存中毒（memory poisoning）**：一个智能体产生幻觉“事实”，其他智能体将其当作已验证的信息，并且准确性逐渐下降，比立即崩溃更难调试。本课通过stdlib构建两种结构，注入中毒攻击，并展示三种生产中真正有效的缓解措施。

**类型：** 学习 + 构建  
**语言：** Python（stdlib，`threading`）  
**前置条件：** Phase 16 · 04（原始模型），Phase 16 · 09（并行群体网络）  
**时间：** ~75分钟

## 问题

多智能体系统需要一个共享事实的地方。一个直观选项是“通过消息传递一切”——但这相当于用额外复制重新发明了共享状态。另一种是“给每个人一个全局日志”——全球日志无界增长且容易中毒。第三种是“为每个智能体投影视图”——可扩展，但需要复杂的模式设计。

当某个智能体产生幻觉并将其写入共享状态时，所有读取该状态的下游智能体都将幻觉当作事实。直到人类发现问题时，推理链可能已经五步深入，根本原因是写入的第三条消息。调试多智能体精准度下降比调试崩溃要难。

这就是内存中毒（memory poisoning）。它是MAST分类法中第二大最常见的失败家族（Cemri等人，arXiv:2503.13657），其本质是结构性的：任何无来源追踪（provenance）且无写保护验证器的共享内存设计终将出现此问题。

## 概念

### 两种主要拓扑

**完整消息池（Full message pool）**。每个智能体读取所有消息。AutoGen GroupChat和MetaGPT使用这种。简单、透明、可检查，但当智能体数量超过~10时不再可扩展，因为每个智能体的上下文会被其他智能体的工作填满。

```text
agent-A ──写──▶ ┌────────────────┐ ◀──读── agent-D
                  │ message pool   │
agent-B ──写──▶ │                │ ◀──读── agent-E
                  │ (global log)   │
agent-C ──写──▶ └────────────────┘ ◀──读── agent-F
```

**带订阅的黑板（Blackboard with subscription）**。智能体声明感兴趣的话题，底层机制只路由相关消息。CA-MCP（arXiv:2601.11595）和Matrix去中心化框架（arXiv:2511.21686）采用此方法。更易扩展，但需要前期设计模式以使订阅有意义。

```text
                  ┌─ 话题：价格 ──┐
agent-A ──发布──▶ │               │ ──▶ 订阅的 agent-D
                  ├─ 话题：订单 ──┤
agent-B ──发布──▶ │               │ ──▶ 订阅的 agent-E
                  ├─ 话题：预警 ──┤
agent-C ──发布──▶ │               │ ──▶ 订阅的 agent-F
                  └───────────────┘
```

### 各自适用场景

- **完整消息池**适用于智能体少（<10）、异质性强、短期对话场景。每个人看到所有内容，推理谁说了什么极其简单。
- **黑板**适合智能体多、角色相同但实例众多（群体模式）、长期对话。路由节省令牌成本和上下文污染。

生产系统通常混合使用：上层少量完整消息池（规划层），下层黑板（工作层）。

### 内存中毒示例

三个智能体合作研究任务。智能体A负责检索，B负责总结，C负责分析。

1. A抓取网页，写消息至共享状态：“研究报告42%准确率提高。”
2. 实际网页写的是“4.2%提高。”A产生了十进制幻觉。
3. B读共享状态，写：“报告了大幅42%准确率提升（来源：A）。”
4. C读共享状态，写：“推荐采纳——42%提升非常关键。”
5. 最终报告引用了一个不存在的42%数字。

无智能体崩溃，无测试失败，系统“正常运行”。幻觉从A的上下文通过共享状态传递到所有下游智能体。

### 结构原因

无共享状态时，A的幻觉只存在其上下文。下游智能体会重新抓取或推导，可能发现错误。用天真的共享状态，A的上下文变成了所有人的上下文，幻觉被当作事实。

问题不是共享状态本身——是无来源追踪且无独立验证器的共享状态。以下三种缓解措施应运而生：

1. **为所有写入记录来源（provenance）。** 共享状态中每条目记录写入者、时间、提示哈希和（如适用）引用来源。下游智能体带着怀疑读取，根据来源决定信任度。
2. **版本写入；视为追加日志。** 纠正是写入新的条目覆盖旧条目，而非原地更新。审计轨迹得以保留。
3. **保持至少一个不可写共享状态的智能体。** 一个只读验证器智能体抽查条目，重新抓取引用来源并标记不一致。由于不可写共享池，不能被池污染。

### 黑板模式先例（Hayes-Roth，1985）

黑板模式比LLM智能体早40年。Hayes-Roth（1985年，“黑板架构的控制”）描述专家知识源观察全局黑板，贡献局部解，并触发其他知识源。2026年黑板（CA-MCP，Matrix）即用LLM作为知识源，JSON数据作为局部解的同样模式。早期文献里有对写冲突、机会主义控制和一致性问题的解决方案，现代系统不断复现。

### 投影视图与全量视图

纯黑板给订阅者同一投影（话题范围）。更激进设计是**每智能体投影**：每个智能体获得定制对应角色的视图。LangGraph的状态合并器是2026年的典型实现——合并函数将全局状态折叠为角色专属片段。

每智能体投影可进一步扩展但必须有模式设计。无模式则必须在每个智能体提示中重建即兴投影。

### 写入冲突模式

多个智能体同时写入是并发问题，不仅是LLM问题。三种方式：

- **序列化写入者（单生产者）。** 所有写入通过一个协调智能体串行化。简单，但瓶颈。
- **版本乐观并发控制。** 每条目有版本号，写入者版本不匹配即失败重试。经典数据库手法。
- **话题分区。** 不同智能体拥有不同话题，避免跨话题冲突。需设计分区边界。

大多数2026框架默认用序列化写入，因为LLM调用够慢，冲突少且瓶颈影响小。

### 不可写验证器

最关键缓解是只读验证器。实现规则：

- 验证器共享状态（读黑板或消息池）。
- 验证器无共享状态写权限，仅发到独立验证通道。
- 验证器独立抓取引用的来源，标记不一致。
- 验证器输出送人类或独立决策智能体，勿回写池中。

无此分离验证器输出变为池中条目，会被污染的池同样污染验证器，反过来影响验证结果。

## 构建它

`code/main.py`用stdlib Python实现两种拓扑，加演示用的中毒攻击和三种缓解。

- `MessagePool` — 线程安全追加日志，全量读取。
- `Blackboard` — 以话题为键的发布订阅，支持每智能体订阅。
- `ProvenanceEntry` — 每条写入记录（写入者、时间戳、提示哈希、引用来源）。
- `PoisoningScenario` — 运行三智能体研究任务，智能体A产生十进制幻觉。打印最终报告。
- `Verifier` — 只读验证器，重新抓取来源标记不一致。带验证器运行相同场景。

执行：

```text
python3 code/main.py
```

预期输出：
- 第1次运行（无验证器）：幻觉42%传播至最终报告。
- 第2次运行（有验证器）：验证器标记不一致，池标签为“标记（flagged）”，最终报告含撤销说明。

## 使用它

`outputs/skill-memory-auditor.md`是一项技能，审计任何多智能体系统共享内存设计的来源、版本控制和验证器分离。发布前在新系统上运行。

## 交付它

对于任何共享内存设计：

- 每条写入记录来源信息：（写入者、时间戳、提示哈希、调用工具、引用来源）。
- 保持日志追加Only，纠正则写新条目覆盖旧条目。
- 部署至少一个独立读取且有独立来源访问权限的只读验证器智能体。
- 验证器输出路由至独立通道，不回写共享池。
- 记录覆盖率比率（纠正条目占比）——提升说明幻觉模式的早期迹象。

## 练习

1. 运行 `code/main.py`，确认第1次运行传播幻觉，第2次运行捕获幻觉。
2. 添加第二个幻觉：智能体B编造数据集大小。验证器应捕获两个错误，无需针对任意一项手工调优。
3. 将完整消息池切换为话题分区黑板（`prices`，`summaries`，`analyses`）。话题分区减轻了哪些内存中毒场景，哪些场景无帮助？
4. 阅读Hayes-Roth（1985年，“黑板架构的控制”）。找出两种本课程未涉及但2026系统会受益的控制模式。
5. 阅读CA-MCP（arXiv:2601.11595）。将其共享上下文存储映射到`code/main.py`中的MessagePool或Blackboard类。CA-MCP在此基础上增加了哪些原语？

## 关键词

| 术语           | 常见说法           | 实际含义                                              |
|----------------|--------------------|-------------------------------------------------------|
| Message pool   | “共享聊天记录”     | 每个智能体读取的追加日志。完全透明，扩展性差。      |
| Blackboard     | “共享工作区”       | 以话题为键的发布订阅。智能体订阅相关话题。更易扩展。  |
| Provenance     | “谁写了什么”       | 每次写入元数据：写入者、时间戳、提示、来源。          |
| Memory poisoning | “幻觉传播”       | 一智能体错误进入共享状态，下游智能体采用为事实。       |
| Append-only    | “无原地更新”       | 纠正是新条目覆盖旧条目。维护审计轨迹。                |
| Unwritable verifier | “独立审计员”   | 只读智能体，重新抓取来源并标记不一致。                 |
| Projection     | “范围视图”         | 从全局状态计算的每智能体视图。LangGraph合并器示例。   |
| Knowledge Source | “专家智能体”      | Hayes-Roth 1985年对黑板参与者的称呼。                 |
