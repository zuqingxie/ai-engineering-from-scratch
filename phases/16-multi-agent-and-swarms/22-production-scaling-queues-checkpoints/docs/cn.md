# 生产级扩展 — 队列、检查点、持久性

> 将多智能体系统扩展至数千个并发运行需要**持久执行**。LangGraph 的运行时在每个超级步骤后写入一个以 `thread_id` 为键的检查点（默认使用 Postgres）；工作进程崩溃时释放租约，另一工作进程继续执行。智能体可以无限期等待人工输入。**MegaAgent**（arXiv:2408.09955）为每个智能体运行一个具有三种状态（空闲 / 处理 / 响应）和两层协调（组内聊天 + 组间管理聊天）的生产者-消费者队列。**Fiber/async（协程/异步）**优于线程-每任务的方式用于 LLM 流式处理：线程 99% 时间处于空闲等待令牌状态，协程在 I/O 上协同让出。相反观点：Ashpreet Bedi 的《Scaling Agentic Software》（可扩展智能体软件）强调 **FastAPI + Postgres + 无其他组件**，直到负载证明需要扩展——简单架构的表现常超预期。本课构建持久检查点日志、每智能体工作队列及状态转移、异步与线程对比演示，并阐述务实的“从简单开始”原则。

**类型：** 学习 + 构建  
**语言：** Python（标准库，`asyncio`，`sqlite3`）  
**先修：** 第16阶段·09（并行蜂群网络）、第16阶段·13（共享内存）  
**时长：** 约75分钟

## 问题

原型多智能体系统在一台笔记本中运行三个智能体，使用内存事件循环。你要迁移到生产环境：

- 智能体有时运行数小时（长期研究，人工参与等待）。
- 工作进程崩溃，重启丢失状态。
- 峰值负载为平均负载的10倍，需要横向扩展。
- 用户按智能体运行次数付费，需要**精确一次**计费语义。

内存事件循环无法满足这些需求。你需要一个底层持久执行层。2026年主流方案：

1. 带检查点的工作流引擎（Temporal，LangGraph 运行时）。
2. 带状态存储的消息队列（Postgres + SQS/RabbitMQ）。
3. Actor 模型框架（MegaAgent 每智能体生产者-消费者队列）。
4. 手写 FastAPI + Postgres（Bedi 理论）。

本课构建上述每种方案的微型实现。

## 概念

### 持久执行，模式解析

持久执行引擎在每次“步骤”（在 LangGraph 语境中是超级步骤）后持久化完整程序状态。崩溃情况下：

```text
工作进程中断于步骤中
  -> 租约超时
  -> 另一工作进程接管 thread_id
  -> 从上次检查点恢复
  -> 无重复副作用
```

成功要点：

- **可序列化状态。** 智能体所有状态必须可持久化。包含活动数据库连接的闭包不能存活。
- **确定性恢复。** 给定相同状态和输入，智能体产生相同动作（或外包确定性 oracle 处理 LLM 调用）。
- **幂等副作用。** 外部调用（工具调用、支付）必须幂等或使用去重键。

LangGraph 每超级步骤写检查点；Temporal 每活动写；Restate 用事件溯源日志。三者实现相同模式。

### LangGraph 运行时

每个智能体有一个 `thread_id`；状态为类型化字典；每个超级步骤向检查点表追加一行。恢复时，运行时从上次存储的检查点重播，不从头开始。智能体可以通过 `interrupt()` 进入等待人工输入状态；运行时持久化并释放工作进程。输入到达后，任一工作进程可继续。

这是2026年4月的参考生产设计。

### MegaAgent 的每智能体队列

arXiv:2408.09955 描述了一个规模实验：数千并发智能体运行于一个集群。架构：

```text
智能体 i:
  状态 ∈ {空闲, 处理中, 响应中}
  in_queue   <- 发送给智能体 i 的消息
  out_queue  -> 回复及副作用消息

协调器:
  组内聊天  (同组智能体)
  组间管理聊天  (高层路由)
```

两层协调允许组内聊天密集进行而组间聊天保持稀疏——该模式保持数千智能体成本线性增长。

### 异步与线程对比

LLM 调用是I/O密集型。线程等待下一令牌时 99%处于空闲。线程占用约1MB RAM；1万个并发调用即占用10GB内存堆栈。

Fiber（Python 的 `asyncio`，Go 的 goroutines，Rust 的 `tokio`）协作让出I/O。相同1万个调用进程内轻松容纳。在 LLM 智能体规模上，异步非优化而是架构选择。

例外：CPU密集后处理（嵌入、分词技巧）仍需线程或独立进程。将I/O层与CPU层分离。

### Bedi 的反观点

Ashpreet Bedi 2026年的《Scaling Agentic Software》认为许多团队在测量负载前过度设计。务实默认：

- FastAPI + Postgres
- 每智能体运行一行；状态原位更新，乐观并发控制
- 使用 `pg_notify` 或简单的 Celery 任务处理后台作业
- 重试策略写在应用代码

对于约100个并发智能体运行的中等任务，这足够用。出现问题再升级。

原则：只有当简单架构无法解决具体问题时，才采用持久执行框架。过早采用浪费时间在无益架式上。

### 精确一次语义

付费智能体运行需“精确一次有效”（至少一次投递 + 幂等消费者）。工程方案：

- **每运行唯一去重键。** 包含于所有副作用调用。
- **发件箱模式。** 副作用先写表，后有独立进程执行。两步均幂等。
- **补偿事务。** 副作用成功但追踪写入失败时，调度补偿操作。

这都是数据库工程模式，非 LLM 特有。LLM 额外负担就是调用较慢，其他是标准分布式系统问题。

### 彩虹部署

Anthropic 多智能体研究系统使用“彩虹部署”策略：多版本智能体运行时并行存在，避免每次代码部署时杀死长期运行智能体。仅在流量切片上测试新版本；旧版本智能体运行结束后淘汰。

这是长期运行有状态系统的标准做法；2026年的方案是智能体运行时长达数小时，部署周期必须支持。

### 生产环境规范清单

- 持久状态（检查点、快照或发件箱+可回放日志）。
- 幂等副作用。
- 基于异步的 I/O 层处理 LLM 调用。
- 至少一次交付，含去重。
- 彩虹/金丝雀部署支持有状态工作负载。
- 可观测性：智能体级调用链、超级步骤审计、重试计数。

## 构建

`code/main.py` 实现：

- `CheckpointStore` — 基于 SQLite 的检查点日志，使用线程ID作为键。每超级步骤追加一行。
- `run_with_checkpoint(agent, thread_id)` — 模拟运行中崩溃；第二个工作者从上次检查点恢复。
- `AgentQueue` — 每智能体空闲 / 处理中 / 响应状态机及小型工作队列。
- `demo_async_vs_threads()` — 并发运行500个模拟 “LLM 调用”，分别用 asyncio 和线程实现；报告实际耗时和峰值内存（估算）。

运行：

```text
python3 code/main.py
```

预期结果：模拟崩溃后检查点恢复成功；异步版本500个并发调用 < 1秒完成；线程版本耗时数秒，且每并发单元内存占用多量级。

## 部署

生产级加固建议：

- **从简单开始（Bedi 法则）。** FastAPI + Postgres，测出失败再扩展。
- **优化前先监控。** 每运行延迟直方图，步骤用时，重试计数，失败分类。
- **副作用采用发件箱模式。** 尤其是支付和外部API调用。
- **彩虹部署。** 绝不在部署时杀死正在运行的智能体任务。
- **遇具体问题时采用持久执行引擎（Temporal / LangGraph / Restate）。** 例如长时间人工等待、跨区协调、复杂重试/补偿策略。
- **I/O层采用异步。** CPU密集后处理用线程。

## 练习

1. 运行 `code/main.py`。确认检查点恢复；测量异步与线程并发差异。
2. 实现**发件箱**表：每次工具调用先写入发件箱，随后独立 goroutine/任务执行。通过执行工具调用两次验证幂等性。
3. 模拟**彩虹部署**：两个并发运行时版本；新 `thread_id` 一半路由到每个版本；确认旧版本正在运行线程不被中断。
4. 阅读 LangGraph 运行时文档（下方链接）。识别手写 FastAPI + Postgres 版本最难复刻的运行时特性。是否值得采用或可以拖延？
5. 阅读 MegaAgent（arXiv:2408.09955）第三节。两层协调（组内 + 组间管理聊天）明确。绘制如何映射到两个消息队列族的方案草图。

## 关键词

| 术语 | 常见说法 | 实际含义 |
|------|----------|----------|
| Durable execution（持久执行） | “持久化程序状态” | 引擎在每个超级步骤后写入状态；崩溃恢复是确定性的。 |
| Super-step（超级步骤） | “事务边界” | 检查点间的工作单元。LangGraph 术语。 |
| thread_id（线程 ID） | “智能体运行标识” | 绑定检查点和恢复逻辑的键。 |
| Idempotency（幂等性） | “安全重试” | 重复执行副作用产生相同结果。 |
| Outbox pattern（发件箱模式） | “副作用解耦” | 写入意图到表中；独立执行器执行并标记完成。 |
| At-least-once delivery（至少一次投递） | “可能有重复” | 消息队列语义；去重键使消费者具备效果上的单次执行。 |
| Rainbow deploy（彩虹部署） | “版本重叠运行” | 多版本运行时并存，支持长期运行负载。 |
| Async fiber（异步纤程） | “协作让出” | 用户态并发；I/O密集负载比线程更轻量。 |
| Checkpoint（检查点） | “状态快照” | 超级步骤边界序列化状态；恢复关键。 |
