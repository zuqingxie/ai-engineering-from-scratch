# 分层架构及其失败模式

> 分层架构是监督者（supervisor）嵌套的形式。管理者代理（manager agents）监控子管理者（sub-managers），子管理者再监控普通执行者（workers）。CrewAI 的 `Process.hierarchical` 是教科书式实现：一个 `manager_llm` 动态分配任务并验证输出。LangGraph 中对应的是 `create_supervisor(create_supervisor(...))`。当任务本身就是一个真实的组织结构图时，这是自然的模式。但这也是最容易陷入管理循环的模式——管理代理分配工作不当、误解下级输出或无法达成共识。顺序流程通常表现更佳。

**类型：** 学习 + 构建  
**语言：** Python（标准库）  
**先决条件：** 第16阶段·05（监督者模式）  
**时间：** 约60分钟

## 问题

一旦监督者模式奏效，下一步自然是“如果执行者本身也是监督者怎么办？”团队有子团队，公司有部门下设子部门。分层架构正是这种结构的映射。

问题在于：LLM 管理者和人类管理者不同。人类管理者对下属的知识背景有稳定的先验认知，而 LLM 管理者每次都从上下文出发重新推理组织架构。上下文的微小漂移会导致整个树状结构工作分配错误。

## 概念

### 结构形态

```text
                 Manager
                 ┌─────┐
                 └──┬──┘
           ┌────────┴────────┐
           ▼                 ▼
       Sub-Mgr A         Sub-Mgr B
       ┌─────┐           ┌─────┐
       └──┬──┘           └──┬──┘
         ┌┴──┬──┐          ┌┴──┐
         ▼   ▼  ▼          ▼   ▼
       W1  W2  W3         W4  W5
```

每个内部节点负责规划、委派和综合，只有叶节点真正执行工作。

### 优势所在

- **清晰的组织映射。** 如果真实任务是部门级的（“法务审查文档，财务审查文档，工程审查文档，然后给高管总结”），层级结构非常明确。
- **局部总结。** 每个子管理者在顶级管理者看到结果前，先综合其团队的输出。顶级管理者看到的是三个子管理者的总结，而不是十五个执行者的细节。

### 失败场景

2026年多篇事后分析总结了三个失败模式：

1. **任务分配错误。** 管理者读取目标后，误解拆解方案，把任务分配给错误的子管理者。由于子管理者严格执行被分配的工作，错误只会在顶级综合时暴露出来——这已经脱离了人类可以及时发现的层级。
2. **输出误解。** 子管理者返回“无法验证声明 X”，顶级管理者却总结为“声明 X 未被确认”。含义在每个层级发生偏移。
3. **共识循环。** 两个子管理者意见不合，顶级管理者要求他们协调，子管理者重新委派，执行者重复运行，子管理者返回略有差异的答案；形成循环。CrewAI 的 `Process.hierarchical` 用执行步数限制来防止此类循环，但步数限制本身又成为一个超参数。

### 决定性问题

顺序（线性流水线）和分层：你的任务实际上有没有独立的子团队，还是一条线性流程却假装成树形？如果是后者，使用顺序；如果是前者，使用分层且明确预留对账规则。

### CrewAI 的实现

`Process.hierarchical` 将管理者 LLM 与专业团队（specialist crews）连接起来。管理者：

- 接收顶层任务，
- 分配子任务给各团队，
- 评估团队输出，
- 决定接受、重新分配还是迭代。

文档：https://docs.crewai.com/en/introduction （搜索“Hierarchical Process” 在核心概念中）。

### LangGraph 的实现

LangGraph 使用嵌套的 `create_supervisor` 调用。内部监督者有自己的图结构；外部监督者将内部图当作一个不可见节点。这种方式调试更清晰（可以单独跟踪每个图），但动态改变树结构更困难。

参考：https://reference.langchain.com/python/langgraph-supervisor

## 实践构建

`code/main.py` 运行三层分层：

- 顶层管理者：将任务拆分为“工程”和“法务”两条分支，
- 工程子管理者：拆分为“前端”和“后端”执行者，
- 法务子管理者：一个执行者。

演示对比顺利路径（各方达成共识）与**扰动路径**，其中顶层管理者的拆分错误地将“法务”标记为“财务”，观察错误如何级联产生——子管理者按指令执行财务工作，顶级综合者报告财务结果，原法务问题悬而未决。

运行：

```text
python3 code/main.py
```

输出显示两条路径，旁边并排清晰对比“被提问的内容”与“最终交付内容”。

## 使用指南

`outputs/skill-hierarchy-fitness.md` 评估给定任务应使用分层、顺序还是平铺监督者。输入包括任务描述、组织结构、对账预算。输出是模式推荐及需防范的具体失败模式。

## 部署建议

如果采用分层：

- **树深上限为2层。** 三层及以上容易导致大部分错误无法被观察到。
- **明确对账预算。** 设置顶级管理者必须做出承诺的最大轮次，通常为2轮。
- **每次综合都要带出处（provenance）。** 每个节点的总结必须引用是由哪些叶节点的输出生成。
- **对拆分偏移报警。** 每步记录管理者的拆分方案；与用户查询做差异检测。如果不再覆盖原查询，则触发警告。

## 练习

1. 运行 `code/main.py`，比较顺利与扰动路径。顶级输出与用户问题完全偏离需要多少层管理交接？
2. 增加第三级（顶层→子层→子子层→执行者）。衡量扰动路径随着深度增加时，纠正概率与完全偏离概率的变化。
3. 在每个子管理者下实现“金丝雀”工作者，始终被问及原始问题（不变）。用金丝雀答案检测拆分偏移。当金丝雀与综合答案不符时，管理者应如何响应？
4. 阅读 CrewAI `Process.hierarchical` 文档。找出一个明确的防护措施（步数限制、manager_llm 约束等），说明其针对的失败模式。
5. 对比嵌套的 LangGraph 监督者与 CrewAI 分层实现。哪种更容易检测对账循环？

## 关键词

| 术语           | 俗称                                  | 实际含义                                           |
|----------------|-------------------------------------|--------------------------------------------------|
| Hierarchical   | “组织结构模式”                       | 监督者套监督者，只有叶子节点做实际工作。          |
| Manager LLM    | “老板”                              | 在内部节点负责拆解、分配和验证的 LLM。             |
| Decomposition drift | “老板迷失了情节”                | 顶级管理者的拆解不再覆盖原始问题。                |
| Reconciliation loop | “无休止会议”                    | 子管理者意见不合，顶级重复委派，执行者反复运行，直到预算耗尽。 |
| Depth-2 ceiling | “不要超过2层深度”                   | 经验防护：3层及以上丧失可观测性。                 |
| Canary question | “每层真相监测”                     | 始终以未变更的原始问题问某执行者，用于检测拆解偏移。  |
| Provenance chain | “谁说了什么”                      | 从每次总结回溯到产生该输出的叶节点。              |
