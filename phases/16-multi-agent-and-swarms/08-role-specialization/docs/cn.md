# 角色专精 — 规划者（Planner）、批评者（Critic）、执行者（Executor）、验证者（Verifier）

> 2026年最常见的多智能体分工：一个负责规划，一个负责执行，一个负责批评或验证。MetaGPT（arXiv:2308.00352）将其形式化为编码进角色提示（role prompts）的SOP（标准操作程序）——产品经理（Product Manager）、架构师（Architect）、项目经理（Project Manager）、工程师（Engineer）、QA工程师（QA Engineer）——遵循`Code = SOP(Team)`。ChatDev（arXiv:2307.07924）通过“聊天链”串联设计师、程序员、审查者和测试者，采用“沟通式去幻觉”（communicative dehallucination）（智能体在缺失细节时明确请求）。验证者是承重的角色：Cemri等人（MAST, arXiv:2503.13657）表明每个多智能体失败都可追溯到缺失或失效的验证。普华永道报告称CrewAI中结构化验证循环实现了7倍准确度提升（10% → 70%）。

**类型：** 学习 + 构建  
**语言：** Python（标准库）  
**先决条件：** 第16阶段 · 04节（原始模型），第16阶段 · 05节（监督者）  
**时间：** 约60分钟

## 问题

通用多智能体系统只能产生通用输出。三个编码者在群聊中写出三种不同风格但都平庸的代码。你可以增加更多智能体、增加更多轮次，仍然无法突破质量门槛。

解决方案不是增加更多智能体，而是*不同类型*的智能体。分配不同职责。赋予批评者规划者没有的工具。给验证者提供一个客观的测试套件。这样系统内部有不一致意见和有根有据的修正，而不仅是平行猜测。

## 概念

### 四个典型角色

**规划者（Planner）**。阅读目标，输出步骤列表或规范。工具：知识检索、文档。输出：结构化计划。

**执行者（Executor）**。逐步读取计划，产出成果。工具：实际工作工具（代码编译器、shell、API客户端）。输出：产物。

**批评者（Critic）**。根据规划者意图检查执行者的输出。工具：只读访问产物、静态分析。输出：接受/拒绝及理由。

**验证者（Verifier）**。检验产物并运行确定性检查。工具：测试运行器、类型检查器、模式校验器。输出：通过/失败及证据。

批评者是主观的、有观点的，通常基于大语言模型（LLM）。验证者是客观的、确定性的，通常基于代码。两者不是同一角色。

### MetaGPT的SOP模式

MetaGPT（arXiv:2308.00352）将软件工程SOP编码为角色提示：

- **产品经理（Product Manager）** 编写PRD。
- **架构师（Architect）** 设计系统架构。
- **项目经理（Project Manager）** 拆分任务。
- **工程师（Engineer）** 实现代码。
- **QA工程师（QA Engineer）** 执行测试。

每个角色都有严格的输入/输出规范。角色提示定义角色*是什么*以及必须产出*什么*。`Code = SOP(Team)` 公式——确定性的SOP将一组LLM团队转成可预测的流水线。

### ChatDev的沟通式去幻觉

ChatDev 增加了关键步骤：当执行者需要计划中未包含的具体细节时，会在继续之前明确向设计者询问。这防止了LLM凭空编造细节的经典失败。

实现方式：角色提示内包含“当你需要未提供的具体信息时，应在产出前向相关角色明确提问”。

### 为什么验证者最重要

Cemri等人（MAST）追溯了1642例多智能体执行失败。21.3%是验证缺失——系统交付了没人检查的答案。其余79%往往因“有检查，但默默失败或根本未执行”。验证者是承重角色。

普华永道（CrewAI部署，2025）报告称，添加结构化验证循环使准确率从10%提升到70%。一角色情况下7倍提升。

### 批评者与验证者的区别

- 批评者是由LLM组成的质量审核者。主观，容易被合理的文字蒙蔽。
- 验证者是对产物运行确定性检测的程序。客观，生成通过/未通过及证据。

两者结合使用。批评者捕捉验证者无法表达的品味问题。验证者发现批评者看不到的仅在运行时显现的缺陷。

### 反模式

系统内每个角色都是LLM，每个角色输出都是“看起来没问题”。经典MAST失败模式。至少添加一个由代码决定通过/失败的验证者，避免全LLM。

### 框架映射

- **CrewAI** — `Agent(role, goal, backstory)` 是教科书式的角色专精接口。
- **LangGraph** — 节点可带有专门提示，边缘保证流水线执行。
- **AutoGen** — 角色专用的ConversableAgents，在GroupChat中用单词命名。
- **OpenAI Agents SDK** — 专门化角色智能体间的交接工具。

## 构建它

`code/main.py` 实现了一个4角色流水线，构建一个简单的Python函数：

- **规划者** 制定规范。
- **执行者** 生成代码字符串。
- **批评者**（LLM模拟）标记明显问题。
- **验证者** 在沙箱中运行生成的代码（`exec`），并对测试用例进行验证。

演示运行两次：一次执行者生成正确代码（批评者和验证者均通过），一次生成偏离规范代码（批评者因表面合理错过bug，验证者因测试失败捕获）。

运行命令：

```text
python3 code/main.py
```

## 使用它

`outputs/skill-role-designer.md` 拿一个任务，产生角色列表（3-5个角色）、每个角色的输入/输出规范及验证者检查。在将智能体接入框架前使用。

## 交付它

检查列表：

- **至少一个确定性验证者。** 绝不全是LLM。
- **每个角色明确输入/输出规范。** 规划者输出规范而非自由文本，执行者按规范理解。
- **沟通式去幻觉。** 执行者缺信息时必须询问规划者，绝不伪造。
- **批评者/验证者排序。** 先运行批评者（便宜，捕获设计问题），再运行验证者（慢，捕获缺陷）。
- **循环预算。** 最多2轮批评者-执行者修正循环，然后升级到人工检查。

## 练习

1. 运行`code/main.py`，观察验证者如何捕获批评者漏掉的bug。添加一个静态分析检查（统计`return`关键字出现次数）作为额外验证。它捕获了运行时测试漏掉了什么？
2. 添加第五个角色：“需求分析师”，负责将用户愿望转为规划者可用的规范。哪些沟通式去幻觉请求应向它传递？
3. 阅读MetaGPT第3节（“Agents”）。列出MetaGPT五个角色的输入/输出规范。
4. 阅读ChatDev的聊天链示意图（arXiv:2307.07924 图3）。指出沟通式去幻觉打破了哪个本将无限循环的环节。
5. PwC的7倍准确率提升来自验证循环。推测三类任务添加验证者不奏效——即无法或代价高昂地进行确定性正确性检测的场景。

## 关键词

| 术语 | 人们所说 | 实际含义 |
|------|----------|----------|
| 角色专精（Role specialization） | “不同智能体，不同任务” | 针对规划者/执行者/批评者/验证者角色调优的独特系统提示。 |
| SOP模式（SOP pattern） | “编码的标准操作程序” | MetaGPT的框架：严格输入/输出规范将团队转成流水线。 |
| 沟通式去幻觉（Communicative dehallucination） | “先问再造” | ChatDev模式：执行者缺细节时向规划者明确询问，不随意编造。 |
| 批评者（Critic） | “LLM审核者” | 主观、有观点的评审。捕捉品味问题。可能被合理文本欺骗。 |
| 验证者（Verifier） | “确定性检查” | 基于代码的通过/不通过。测试运行器、类型检查器、模式校验器。不可被欺骗。 |
| 验证缺口（Verification gap） | “无人校验” | 21.3%的MAST失败案例。交付答案未经过风险检测。 |
| 修正循环（Revision loop） | “批评后返工” | 批评拒绝触发执行者带反馈重跑。有预算限制。 |
| 全LLM反模式（All-LLM anti-pattern） | “看起来不错” | 所有角色都是LLM，没有确定性检查。典型MAST失败。 |
