# 主管 / 协调者-工作者模式

> 一个主管代理负责规划和分配任务；专业化的工作者在并行上下文中执行，并反馈结果。这是Anthropic的Research系统背后的模式（Claude Opus 4担任主管，Sonnet 4为子代理），在内部研究评估中比单代理Opus 4提升了+90.2%。Anthropic的工程文章显示，BrowseComp任务中的方差有80%仅由token使用量解释——多代理胜出主要因为每个子代理都有独立的新上下文窗口。本课时从原语构建主管模式，涵盖2026年生产部署中的工程经验教训。

**类型:** 学习 + 构建  
**语言:** Python（stdlib，`threading`）  
**先决条件:** 第16阶段 · 04（原始模型）  
**时间:** 约75分钟

## 问题

研究是单代理系统失败的典型任务。你会问：“2023年到2026年，多代理系统发生了什么变化？”单代理顺序读取五篇论文，将其文本填满一半上下文窗口，然后必须将它们一起推理。到读到第五篇时，它已经忘记了第一篇。它无法并行处理。

主管模式解决了这个问题：一个主管代理规划搜索，将各子问题委派给工作者，并进行综合。每个工作者获得独立的20万token窗口用于窄域问题。主管从不直接阅读原始论文——只看到工作者的摘要。

Anthropic的生产Research系统相比单Opus 4，在内部研究评测中提高了+90.2%。同一文章指出，BrowseComp的80%方差由*token使用量*单独解释。每个子代理独立的上下文是主要机制。

## 概念

### 模式结构

```text
                 ┌──────────────┐
                 │   主管       │  规划、拆解、
                 │  (Opus 4)    │  综合
                 └──┬────┬───┬──┘
                    │    │   │
            ┌───────┘    │   └───────┐
            ▼            ▼           ▼
      ┌─────────┐  ┌─────────┐  ┌─────────┐
      │ 工作者1 │  │ 工作者2 │  │ 工作者3 │
      │(Sonnet) │  │(Sonnet) │  │(Sonnet) │
      └─────────┘  └─────────┘  └─────────┘
         独立       独立        独立
         上下文     上下文      上下文
```

主管从不直接读取原始材料。工作者之间不会看到彼此的工作，直到主管进行综合。每个箭头代表带有窄域结果的交接。

### 为什么会赢

三个机制：

1. **每个子代理独立新上下文。** 研究“FIPA-ACL传承”的工作者不会携带主管规划时用掉的4万token。它获得20万token窗口问一个问题。
2. **基于提示实现专业化。** 主管的提示是“拆解和综合”，而非“研究”。每个工作者的提示都很窄：“找出X的变化”。专注的提示产生专注的输出。
3. **并行执行。** 工作者并发运行。实际时间大致是`max(工作者耗时) + 规划 + 综合`，而非`工作者耗时之和`。

### 工程经验教训（Anthropic 2025）

Anthropic文章列出了多条仍然适用的2026年经验：

- **按查询复杂度调节工作量。** 简单查询：1个代理，3-10次工具调用。复杂查询：10+代理。主管负责评估，不是调用方。
- **先广泛再细化。** 先将问题拆解为广泛子问题，然后根据答案深度继续增加子代理。
- **彩虹部署。** 代理是长运行且有状态的。传统蓝绿部署不可行。Anthropic用彩虹部署：更新版本逐步上线，旧版本逐渐退出。
- **Token使用量主导成本。** 多代理约为单代理的15倍token使用。只有当任务价值足够时才运行。

### LangGraph的转变

LangGraph最初提供了`langgraph-supervisor`库，带高级`create_supervisor`辅助函数。2025年，LangChain推荐通过工具调用方式实现主管模式，因为工具调用能更好控制*主管能看到什么*（上下文工程）。该库依旧可用，但文档推荐使用工具调用形式。

### 失败模式

- **主管幻想规划。** 若主管生成的子问题未真正拆解主体问题，工作者会精准研究错误目标。
- **工作者过度探索。** 若无明确范围边界，工作者会超出委派问题范围，导致综合污染。
- **综合冲突。** 两个工作者返回矛盾事实。主管必须重新提问（增加一轮）或显式标注分歧。默默选择一方是最糟失败，用户永远不知道分歧存在。

### 主管模式不适用时

- **顺序任务。** 若步骤2必须依赖步骤1输出，并行无益。用流水线（CrewAI 顺序，LangGraph 线性图）。
- **简单查询。** 单代理更快更便宜。用主管的“匹配工作量”判定是否派生工作者。
- **严格确定性。** 主管用LLM择定委派。需要审计/重放时，静态图更好。

## 构建它

`code/main.py`实现用`threading`的主管与三个并行工作者。主管拆解查询成子问题，工作者并发运行，主管进行综合。没有真实LLM——工作者脚本模拟获取和总结。

核心结构：

- `Lead.plan(query)`将查询拆成3个子问题。
- `Worker.run(sub_q)`返回伪造摘要（生产可替换任意工具代理）。
- `Lead.run(query)`开启工作线程，等待并综合。

运行：

```text
python3 code/main.py
```

输出显示规划、并行工作者的开始/结束时间戳轨迹和最终综合。你能明显看到时间优势：三个0.3秒工作者大约在0.35秒内完成，而非0.9秒。

## 使用方法

`outputs/skill-supervisor-designer.md`可接收用户查询并产生主管模式设计：主管系统提示、工作者角色、子问题拆解规则及综合模板。构建新研究型代理系统前建议先用此工具设计。

## 部署注意事项

部署主管模式前检查：

- **模型配对。** 主管用推理级模型（Opus系列、`o3`系列）。工作者用更快、更廉价模型（Sonnet、`o4-mini`）。
- **工作者超时。** 超过中位运行时2倍的工作者被终止；主管重新派发更细范围或忽略其结果。
- **每工作者token上限。** （例如综合输入的10倍）防止失控工作者暴增预算。
- **可观测性。** 追踪主管规划、工作者工具调用及综合结果。是任何事后调试基础。
- **彩虹滚动。** 有状态长运行代理需逐步版本迁移，非热交换。

## 练习

1. 运行 `code/main.py`，然后修改主管生成5个工作者而非3个。观察壁钟时间。此Demo中多少个工作者后派生开销超过并行节省？
2. 实现工作者超时：杀死运行超过0.5秒的工作者，并让主管综合剩余结果。你需要什么可观测信息以确认工作者被切断？
3. 在主管综合步骤加入冲突检测：若两工作者答案矛盾，主管标注分歧而非选一方。如何不用调用LLM检测矛盾？
4. 阅读Anthropic Research系统工程文章。列举三个此示例须采用的生产实践。
5. 比较LangGraph的`create_supervisor`（遗留）与新推荐工具调用方式。哪个能更好控制主管能看到什么？为何Anthropic显式只传递子答案而非原始工作者上下文进入综合？

## 术语表

| 术语           | 大众说法           | 实际含义                                           |
|----------------|--------------------|--------------------------------------------------|
| Supervisor     | “主管代理”         | 规划、分配、综合的协调代理。不亲自完成具体工作。     |
| Worker         | “子代理”           | 主管调用的聚焦代理，职责窄，独立上下文窗口。           |
| Orchestrator-worker | “主管模式”     | 同义不同称。2026年文献均使用此两个说法。                 |
| Fresh context  | “干净窗口”         | 工作者上下文从系统提示和子问题开始，不含主管历史。       |
| Rainbow deployment | “逐渐发布”       | 有状态长运行代理需版本化逐步替换，不是蓝绿部署。         |
| Token dominance| “上下文才是关键变量”| Anthropic认为研究评测80%方差由token总用量决定，非模型。   |
| Scale effort   | “匹配代理数与复杂度” | 主管评估查询难度，相应生成1个或10+个工作者。             |
| Synthesis conflict | “工作者意见不合”| 两工作者返回矛盾事实，主管必须显式表现分歧，不可默选一方。 |
